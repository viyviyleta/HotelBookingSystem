## 2. Часть 1. Deployment и проверка развёртывания

### 2.1. Deployment

Файл `k8s/deployment.yaml` (ключевые фрагменты):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: riot-server
  labels:
    app: riot-server
spec:
  replicas: 3
  selector:
    matchLabels:
      app: riot-server
  template:
    metadata:
      labels:
        app: riot-server
    spec:
      initContainers:
        - name: wait-for-db
          image: postgres:17-alpine
          imagePullPolicy: IfNotPresent
          command:
            - sh
            - -c
            - until pg_isready -h riot-db -p 5432 -U postgres -d hotelbooking; do echo "waiting for riot-db"; sleep 2; done
      containers:
        - name: server
          image: riot-server:1.0
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 5377
              name: tcp-server
          readinessProbe:
            tcpSocket:
              port: 5377
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3
          env:
            - name: APP_MODE
              valueFrom:
                configMapKeyRef:
                  name: riot-config
                  key: APP_MODE
            - name: SERVER_PORT
              valueFrom:
                configMapKeyRef:
                  name: riot-config
                  key: SERVER_PORT
            - name: SERVER_STORAGE
              value: postgres
            - name: SERVER_SYNC
              value: lock
            - name: REPLICATION
              value: "on"
            - name: PUBSUB
              value: "on"
            - name: CLUSTER
              value: "on"
            - name: CLUSTER_NODES
              value: "5"
            - name: DB_HOST
              value: riot-db
            - name: DB_PORT
              value: "5432"
            - name: DB_NAME
              value: hotelbooking
            - name: DB_USER
              value: postgres
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: riot-db-secret
                  key: DB_PASSWORD
```

Назначение полей:

- `replicas` — желаемое количество Pod; в актуальном манифесте зафиксировано итоговое значение
  `3` (при первом применении в части 1 использовалось `1`, затем выполнено масштабирование);
- `selector.matchLabels` и `template.metadata.labels` — метка `app: riot-server`; по ней
  Deployment управляет Pod, а Service выбирает их;
- `image` — образ из ЛР №8;
- `containerPort: 5377` — документируемый порт приложения; сам по себе он не публикует порт;
- `readinessProbe` — проверяет, что приложение действительно слушает `5377`; пока проверка
  не проходит, Pod не получает трафик через Service;
- `initContainer wait-for-db` — ждёт готовности PostgreSQL. Без него первый запуск сервера
  завершил инициализацию БД с ошибкой `Failed to connect to 10.96.119.255:5432`, потому что
  Pod базы ещё не был готов. После добавления init-контейнера сервер стартует только тогда,
  когда `pg_isready` подтвердит доступность БД.

### 2.2. PostgreSQL и Secret

Файл `k8s/postgres.yaml` создаёт Deployment `riot-db` и Service `riot-db`:

- образ `postgres:17-alpine`;
- `POSTGRES_DB=hotelbooking`, `POSTGRES_USER=postgres`;
- пароль берётся из Secret `riot-db-secret`, ключ `DB_PASSWORD`;
- readiness-проба `pg_isready`;
- том `emptyDir` для `/var/lib/postgresql/data`.

Secret создан из значения `DB_PASSWORD` файла `.env`:

```bash
kubectl create secret generic riot-db-secret \
  --from-literal=DB_PASSWORD="$DB_PASSWORD" \
  --dry-run=client -o yaml | kubectl apply -f -
```

Пароль не хранится в манифестах и не выводится в отчёт. Шаблон Secret находится в
`k8s/secret.yaml.example`, реальный `k8s/secret.yaml` добавлен в `.gitignore`.

Ограничение учебной конфигурации: `emptyDir` удаляется вместе с Pod базы. Для сохранения данных
между пересозданиями Pod нужен `PersistentVolumeClaim`, но в локальной учебной среде достаточно
`emptyDir`; после пересоздания БД сервер повторно создаёт схемы и заполняет комнаты.

## 3. Часть 2. Service и доступ к приложению

### 3.1. Service

Файл `k8s/service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: riot-server
  labels:
    app: riot-server
spec:
  type: ClusterIP
  selector:
    app: riot-server
  ports:
    - name: tcp-server
      port: 5377
      targetPort: 5377
      protocol: TCP
```

Параметры:

- `type: ClusterIP` — Service доступен внутри кластера;
- `selector: app: riot-server` — совпадает с меткой Pod из Deployment;
- `port: 5377` — порт Service;
- `targetPort: 5377` — порт контейнера;
- `protocol: TCP` — приложение использует TCP.

Проверка (`04-service.log`):

```
$ kubectl get svc riot-server
```

Селектор Service и метки Pod совпадают, поэтому endpoints содержат адреса всех готовых Pod.
При масштабировании endpoints автоматически обновляются.

### 3.2. Доступ с локального компьютера

```bash
kubectl port-forward svc/riot-server 5377:5377
# Forwarding from 127.0.0.1:5377 -> 5377
# Forwarding from [::1]:5377 -> 5377
```

Клиент запускается на компьютере и обращается к `127.0.0.1:5377`. `port-forward` перенаправляет
соединения на Service, а Service — на один из готовых Pod. Клиент не выбирает Pod вручную.
Команда должна оставаться запущенной на протяжении эксперимента.

## 4. Часть 3. Масштабирование и восстановление после удаления Pod

### 4.1. Масштабирование 1 → 3

```bash
kubectl scale deployment/riot-server --replicas=3
kubectl rollout status deployment/riot-server
kubectl get deploy, pods, endpoints
```

Результат (`06-scale.log`):

```
NAME          DESIRED   READY
riot-server   3         3

NAME                           READY   STATUS    RESTARTS   AGE   IP
riot-server-655995495d-k9fw9   1/1     Running   0          108s  10.244.0.18
```

Все три Pod запустились, endpoints содержат три адреса. Клиент по-прежнему обращается к одному

При уменьшении количества Kubernetes завершил лишний Pod и убрал его из endpoints. При

### 4.6. Ответы на вопросы части 3

**Почему Kubernetes создал замену удалённому Pod?**
Deployment хранит желаемое состояние — `replicas: 3`. Контроллер сравнивает его с фактическим
числом Pod и создаёт недостающий Pod. Удаление Pod — это отклонение от желаемого состояния.

**Как Deployment определяет желаемое количество экземпляров?**
Из поля `spec.replicas`. При `kubectl scale` это поле обновляется, после чего ReplicaSet
приводит количество Pod к новому значению.

**Почему количество Pod может временно отличаться от заданного?**
Новый Pod нужно создать, запустить init-контейнер, дождаться готовности БД и пройти
readiness-проверку. В это время он ещё не готов и может не входить в endpoints. При
масштабировании вниз Pod завершается не мгновенно.

**Почему наличие трёх Pod не гарантирует сохранность данных при отказе базы данных?**
Pod сервера не хранят данные предметной области; они работают с общей PostgreSQL. Если Pod
базы потерян вместе с `emptyDir`, данные исчезнут, сколько бы экземпляров сервера ни работало.
Для сохранности нужен PersistentVolume и резервное копирование.

**Почему масштабирование не всегда приводит к ускорению приложения?**
Все экземпляры используют одну базу и общий набор данных; операции сериализуются блокировками
и транзакциями. Узкое место может быть в БД, а не в количестве Pod. Кроме того, в локальном
кластере все Pod работают на одном узле и делят его процессор, память и диск.

## 5. Часть 4. ConfigMap, диагностика и итоговое тестирование

### 5.1. ConfigMap

Файл `k8s/configmap.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: riot-config
  labels:
    app: riot-server
data:
  APP_MODE: "kubernetes"
  SERVER_PORT: "5377"
```

`APP_MODE` — неконфиденциальный параметр режима работы, который приложение читает и выводит
в журнал. `SERVER_PORT` также вынесен в ConfigMap, чтобы показать изменение порта без сборки
нового образа и использовать его для намеренной ошибки.

В коде C# параметр читается в `Server/EnvironmentConfig.cs`:

```csharp
public static string ResolveAppMode(string? value) =>
    string.IsNullOrWhiteSpace(value) ? "default" : value.Trim();

public static string ReadAppMode() =>
    ResolveAppMode(Environment.GetEnvironmentVariable("APP_MODE"));
```

Значение сохраняется в `ServerConfig.AppMode` и выводится при старте:

```
[SERVER] appMode=kubernetes
[SERVER] Running on port 5377, sync mode: lock, application mode: kubernetes
```

### 5.2. Передача параметра в Deployment

```yaml
env:
  - name: APP_MODE
    valueFrom:
      configMapKeyRef:
        name: riot-config
        key: APP_MODE
  - name: SERVER_PORT
    valueFrom:
      configMapKeyRef:
        name: riot-config
        key: SERVER_PORT
```

Имя ConfigMap (`riot-config`) и ключи (`APP_MODE`, `SERVER_PORT`) совпадают с манифестом.
Переменные окружения уже запущенного процесса не меняются автоматически, поэтому после
изменения ConfigMap выполнен `kubectl rollout restart deployment/riot-server`.

## 8. Сравнение Docker и Kubernetes

| Критерий | Docker / Docker Compose (ЛР №8) | Kubernetes (ЛР №9) |
|---|---|---|
| Основная задача | сборка образа и запуск контейнеров; Compose описывает несколько сервисов локально | оркестрация: поддерживает желаемое состояние, количество экземпляров и доступность |
| Описание конфигурации | `Dockerfile`, `compose.yaml` | YAML-манифесты `Deployment`, `Service`, `ConfigMap`, `Secret` |
| Запуск приложения | `docker compose up` запускает контейнеры на одном хосте | `kubectl apply -f k8s/`; контроллеры создают Pod на узлах кластера |
| Управление экземплярами | ручное масштабирование через `--scale` или несколько сервисов | `replicas` в Deployment; контроллер сам создаёт и удаляет Pod |
| Организация доступа | имя сервиса и `ports` в Compose, сеть Docker | Service с селектором, ClusterIP и `port-forward` для локального доступа |
| Изменение количества экземпляров | `docker compose up --scale server=3`, ручная проверка | `kubectl scale deployment/riot-server --replicas=3`, автоматическое обновление endpoints |
| Реакция на удаление контейнера/Pod | Compose перезапускает контейнер согласно `restart`, но не управляет количеством экземпляров как Deployment | Deployment замечает отклонение от `replicas` и создаёт новый Pod |
| Диагностика ошибок | `docker ps`, `docker logs`, `docker inspect`, события Compose | `kubectl get/describe pods`, `kubectl logs`, `kubectl get events`, состояние rollout |
| Требования к среде | Docker Engine и Compose на одной машине | кластер Kubernetes (Docker Desktop, Minikube), `kubectl`, доступ к образу на узле |

Docker отвечает за упаковку и запуск контейнера, Kubernetes — за управление развёртыванием,
количеством экземпляров, доступом и восстановлением. Kubernetes использует те же Docker-образы,
но добавляет контроллеры, декларативное состояние и сетевую абстракцию Service.

  репликация, PUB/SUB, кластер и консенсус;
- запускается в Docker-контейнере, развёрнутом в Kubernetes (`riot-server:1.0`);
- принимает TCP-запросы на порту `5377`;
- выполняет операции предметной области;
- читает параметры `APP_MODE`, `SERVER_PORT`, `DB_*`, `REPLICATION`, `PUBSUB`, `CLUSTER`;
- ведёт журнал с режимом приложения, состоянием БД, ролями узлов и результатами операций;
- корректно обрабатывает ожидаемые ошибки (невалидный JSON, несуществующие объекты, повторные
  операции, недоступность БД);
- не использует `localhost` для обращения к БД: `DB_HOST=riot-db` — имя Service;
- продолжает работу при недоступности БД, сообщая об ошибке в ответах и журнале.

### Клиент

- подключается к серверу по `--host` и `--port`;
- выполняет операции предметной области и отображает результаты;
- отображает сообщения об ошибках;
- позволяет проверить работу до и после развёртывания в Kubernetes;
- через `kubectl port-forward` обращается к `127.0.0.1:5377`;
- сценарии `docker-operations`, `docker-errors`, `docker-state` использованы для проверки.

### Конфигурация Kubernetes

- `k8s/deployment.yaml` — Deployment серверного приложения с образом `riot-server:1.0`;
- `replicas` задаёт количество экземпляров (в манифесте 3; в работе менялось 1 → 3 → 2 → 3);
- `k8s/service.yaml` — Service `riot-server`, селектор совпадает с метками Pod, порт `5377`;
- `k8s/configmap.yaml` — ConfigMap `riot-config` с `APP_MODE` и `SERVER_PORT`;
- `k8s/postgres.yaml` — Deployment и Service `riot-db`, пароль из Secret;
- порядок применения всех манифестов описан в разделе 12;
- конфигурация позволяет масштабировать, удалять Pod, диагностировать ошибки и исправлять их.

## 10. Ответы на контрольные вопросы

**1. Что такое Kubernetes и для чего он используется?**
Платформа оркестрации контейнеризированных приложений. Она описывает желаемое состояние
(образ, количество экземпляров, порты, конфигурацию) и поддерживает его: создаёт Pod, заменяет
удалённые, распределяет трафик через Service, хранит конфигурацию в ConfigMap.

**2. Чем Kubernetes отличается от Docker?**
Docker создаёт образы и запускает отдельные контейнеры. Kubernetes управляет множеством
контейнеров на кластере: масштабированием, восстановлением, сетью и конфигурацией.
Docker Compose — локальный запуск нескольких контейнеров, Kubernetes — оркестрация кластера.

**3. Что такое Kubernetes Cluster?**
Набор узлов и управляющих компонентов, на которых выполняются Pod. В работе кластер
представлен одним узлом `desktop-control-plane`.

**4. Что такое Pod?**
Минимальная единица развёртывания Kubernetes. Содержит один или несколько контейнеров,
совместно использующих сеть и тома. В работе один Pod содержит контейнер сервера.

**5. Чем Pod отличается от Docker Container?**
Контейнер — процесс, запущенный из образа. Pod — обёртка Kubernetes над контейнером(ами),
которая получает собственный IP в кластере, может содержать несколько контейнеров и
пересоздаётся контроллером при удалении.

**6. Что такое Deployment?**
Ресурс, описывающий желаемое состояние приложения: образ, количество реплик, метки, порты,
переменные окружения. Управляет ReplicaSet и Pod, выполняет rolling update.

**7. Для чего используется параметр `replicas`?**
Задаёт желаемое количество Pod. Deployment поддерживает это количество: создаёт недостающие
Pod и удаляет лишние. В работе `replicas` менялось 1 → 3 → 2 → 3.

**8. Что такое Service?**
Стабильная точка доступа к группе Pod. Service выбирает Pod по меткам и предоставляет
единый IP/порт, даже если Pod пересоздаются и меняют адреса.

**9. Почему клиенту неудобно обращаться к Pod напрямую?**
IP Pod нестабилен: при пересоздании Pod получает новый адрес. Клиенту пришлось бы отслеживать
все Pod и выбирать живой. Service скрывает это и балансирует запросы.

**10. Для чего используются метки и селекторы?**
Метки — пары «ключ-значение» для объектов. Селектор — правило выбора объектов по меткам.
Deployment выбирает свои Pod, Service выбирает Pod для трафика. В работе используется
`app: riot-server`.

**11. Что такое YAML и для чего он используется в Kubernetes?**
Текстовый формат структурированных данных. В Kubernetes YAML описывает ресурсы: `apiVersion`,
`kind`, `metadata`, `spec`. Применяется командой `kubectl apply -f`.

**12. Как проверить состояние Pod?**
`kubectl get pods` — краткое состояние; `kubectl get pods -o wide` — IP и узел;
`kubectl get pods -l app=riot-server` — выборка по метке.

**13. Как получить подробную информацию о Pod?**
`kubectl describe pod <имя>` — события, образ, состояние, причины ошибок; `kubectl logs <имя>`
— журнал контейнера.

**14. Что происходит при удалении Pod, управляемого Deployment?**
Deployment обнаруживает, что фактическое количество меньше `replicas`, и создаёт новый Pod.
В работе замена появилась сразу и стала `Ready` примерно через 10 секунд.

**15. Почему восстановление Pod не гарантирует сохранность данных?**
Данные Pod хранятся в его файловой системе или `emptyDir` и исчезают при удалении. Для
сохранности нужны внешняя БД, PersistentVolume или резервное копирование. В работе данные
хранятся в PostgreSQL, но `emptyDir` БД тоже не является постоянным хранилищем.

**16. Что такое ConfigMap?**
Ресурс для неконфиденциальных настроек. Хранит пары «ключ-значение», которые передаются
в контейнер через переменные окружения или тома.

**17. Для чего используются переменные окружения?**
Для передачи процессу параметров во время выполнения без изменения образа: порт, режим,
адрес БД, флаги функций. В работе через них передаются `APP_MODE`, `SERVER_PORT`, `DB_*`.

**18. Для чего используется `kubectl port-forward`?**
Для доступа к Service или Pod с локального компьютера через локальный порт. В работе
`5377:5377` позволил клиенту обращаться к `127.0.0.1:5377`.

**19. Почему несколько Pod на одном компьютере не обеспечивают защиту от отказа этого компьютера?**
Все Pod используют один узел, его процессор, память, диск и сеть. Отказ узла или Docker Desktop
остановит все Pod сразу. Для отказоустойчивости нужны несколько узлов.

**20. Чем Docker Compose отличается от Kubernetes?**
Compose описывает и запускает контейнеры на одном хосте, не поддерживает декларативное
восстановление количества экземпляров и сетевые абстракции кластера. Kubernetes управляет
Pod на кластере, поддерживает `replicas`, Service, rolling update, ConfigMap/Secret и
самовосстановление.

## 12. Как воспроизвести

Полный порядок применения и проверки описан в `k8s/README.md`. Краткая последовательность:

```bash
cd /Users/violettababich/Desktop/Univer/RIOT/HotelBookingSystem

# 1. Проверить кластер
kubectl config current-context          # docker-desktop
kubectl get nodes                       # desktop-control-plane Ready

# 2. Собрать образ (если его нет)
docker build -t riot-server:1.0 -f Server/Dockerfile .

# 3. Создать Secret из .env (значение не выводить)
DB_PASSWORD=$(awk -F= '/^DB_PASSWORD=/{sub(/^DB_PASSWORD=/,""); print; exit}' .env)
kubectl create secret generic riot-db-secret \
  --from-literal=DB_PASSWORD="$DB_PASSWORD" \
  --dry-run=client -o yaml | kubectl apply -f -

# 4. Применить манифесты
kubectl apply -f k8s/configmap.yaml -f k8s/postgres.yaml -f k8s/deployment.yaml -f k8s/service.yaml
kubectl rollout status deployment/riot-db
kubectl rollout status deployment/riot-server
kubectl get pods -o wide

# 5. Доступ с компьютера
kubectl port-forward svc/riot-server 5377:5377
# в другом терминале:
dotnet run --project Client -- --host 127.0.0.1 --port 5377 --scenario docker-operations

# 6. Масштабирование и восстановление
kubectl scale deployment/riot-server --replicas=3
kubectl get pods -l app=riot-server -o wide
kubectl scale deployment/riot-server --replicas=2
kubectl scale deployment/riot-server --replicas=3
kubectl delete pod <имя-pod>
kubectl get pods -l app=riot-server -o wide

# 7. ConfigMap и ошибка
kubectl patch configmap riot-config --type merge -p '{"data":{"SERVER_PORT":"99999"}}'
kubectl rollout restart deployment/riot-server
kubectl get pods -l app=riot-server -o wide
kubectl logs <новый-pod> -c server | grep -E 'Ignored SERVER_PORT|Running on port'
kubectl patch configmap riot-config --type merge -p '{"data":{"SERVER_PORT":"5377","APP_MODE":"kubernetes"}}'
kubectl rollout restart deployment/riot-server
kubectl rollout status deployment/riot-server

# 8. Ошибка с образом
kubectl set image deployment/riot-server server=riot-server:missing-tag
kubectl get pods -l app=riot-server -o wide
kubectl set image deployment/riot-server server=riot-server:1.0
kubectl rollout status deployment/riot-server

# 9. Тесты
dotnet test
```

Удаление ресурсов:

```bash
kubectl delete -f k8s/deployment.yaml -f k8s/service.yaml -f k8s/postgres.yaml -f k8s/configmap.yaml
kubectl delete secret riot-db-secret
```

## 13. Выводы

1. Приложение из ЛР №8 развёрнуто в локальном Kubernetes без изменения предметной логики:
   используется тот же образ `riot-server:1.0` и те же переменные окружения.
2. Deployment поддерживает заданное количество Pod. При масштабировании 1 → 3 созданы три
   экземпляра; при 3 → 2 лишний Pod удалён; при 2 → 3 создан новый.
3. После удаления Pod Deployment восстановил количество до трёх за ~10 секунд. Service
   автоматически исключил удалённый Pod из endpoints и включил новый, поэтому клиентские
   операции не прерывались.
4. Service `riot-server` с селектором `app: riot-server` и портами `5377/5377` обеспечивает
   стабильный доступ; `kubectl port-forward` позволяет клиенту на компьютере обращаться к
   `127.0.0.1:5377`. Клиент не знает, какой именно Pod обработал запрос.
5. ConfigMap `riot-config` передаёт `APP_MODE` и `SERVER_PORT`. Изменение `APP_MODE` видно в
   журнале после перезапуска Pod; запущенный процесс не подхватывает новое значение сам.
6. Намеренная ошибка `SERVER_PORT=99999` привела к предупреждению, запуску на порту `5005` и
   зависанию rolling update: новый Pod не прошёл readiness-проверку на `5377`. Старые Pod
   продолжали обслуживать трафик. После возврата `5377` развёртывание восстановилось.
7. Ошибка с тегом `riot-server:missing-tag` дала `ErrImagePull` и понятное сообщение
   `repository does not exist`; после возврата `riot-server:1.0` Deployment восстановился.
8. Unit-тесты: 253 из 253 пройдены, включая тесты корректных операций, невалидных запросов,
   ожидаемых ошибок и параметра `APP_MODE`.
9. Kubernetes не заменяет механизмы согласованности данных: несколько Pod используют общую БД,
   а `emptyDir` базы не является постоянным хранилищем. Масштабирование не гарантирует
   ускорения, если узкое место — база данных или один узел кластера.
10. Главное отличие: Docker Compose запускает контейнеры, а Kubernetes управляет желаемым
    состоянием, количеством экземпляров, доступом и восстановлением. При этом успешный
    `kubectl apply` не означает, что приложение работает: нужны проверки Pod, readiness,
    endpoints, событий и журналов.
