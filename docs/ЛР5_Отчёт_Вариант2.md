**Вариант 2. Предметная область:** бронирование отелей.

## 0. Цель и ход работы

Цель работы - получить приложение, в котором данные предметной области хранятся в двух
независимых экземплярах (основной Primary и резервный Replica), изменения Primary передаются
в Replica, а при отказе Primary сервер переключает клиентов на Replica и продолжает работать.
После восстановления Primary расхождение копий фиксируется и устраняется синхронизацией.

| Часть | Что выполняется | Где доказательство |
|---|---|---|
| 1 | Организация основной и резервной копий данных | раздел 1, `01-cluster-status.log` |
| 2 | Реализация и проверка репликации | раздел 2, `02-replication.log` |
| 3 | Моделирование отказа и Failover | раздел 3, `03-failover.log` |
| 4 | Восстановление, синхронизация, итоговый анализ, тесты | разделы 4-8, `04-recovery.log`, `05-cycle.log`, `06-errors.log` |

Топология размещения копий (выбран вариант "две схемы в одной базе"):

```
PostgreSQL localhost:5432, база hotelbooking
├── схема riot_primary   → Primary (hotels, rooms, guests, bookings, payments)
└── схема riot_replica   → Replica (те же пять таблиц, копия данных)
```

Способ моделирования отказа (выбран вариант "программа + реальная проверка соединения"):

1. основной способ - сервер помечает экземпляр `UNAVAILABLE` по команде клиента `FailInstance`
   и отказывает в обращении к нему (`InstanceUnavailableException`);
2. независимое подтверждение - копии даётся строка подключения к несуществующей базе
   (`--primary-conn` / `--replica-conn "...;Database=hotelbooking-missing"`), и отказ
   обнаружается настоящей проверкой соединения с ошибкой PostgreSQL `3D000`
   (логи `07-replica-down.log`, `08-primary-down.log`).

## 1. Часть 1. Организация основной и резервной копий данных

### Требование 1. Подготовка проекта

Проект ЛР №4 сохранён без изменений в своей части: клиент-серверное приложение по TCP
с JSON-сообщениями, разделитель `\n`,Modes синхронизации `none|lock`, транзакции
составной операции, журнал `[HH:mm:ss.fff] [Клиент] → событие`. ЛР №5 расширяет слой
доступа к данным: вместо одного `HotelDatabase` появился кластер из двух экземпляров.

```
Client (несколько подключений, параллельная обработка)
   │  Request{Operation, Payload}   /   Response{IsSuccess, Message, Data, EventTriggered}
   ▼
ServerListener → RequestHandler → DbBookingService (IReplicationBookingApi)
   │                                   │
   │                                   ▼
   │        InstanceCluster ── Route(clientId) ── выбор экземпляра под запрос
   │            │        │
   │            │        └── DatabaseInstance Replica (schema riot_replica)
   │            │                 ├── State: AVAILABLE | UNAVAILABLE
   │            │                 ├── Probe(): SELECT COUNT(*) FROM rooms
   │            │                 └── Open(): отказ, если State = UNAVAILABLE
   │            └── DatabaseInstance Primary (schema riot_primary) → HotelDatabase
   │                       │
   │                       ▼  после успешного изменения
   │                  Replicator.ReplicateChange(Primary → Replica)
   │                       ├── INSERT … SELECT … ON CONFLICT (id) DO UPDATE  (bookings)
   │                       ├── INSERT … SELECT … ON CONFLICT (id) DO UPDATE  (payments)
   │                       ├── UPDATE rooms … FROM rooms                     (is_available)
   │                       └── setval(pg_get_serial_sequence(...))           (sequence)
   ▼
PostgreSQL: схема riot_primary | схема riot_replica
```

Журнал событий репликации и переключения ведёт отдельный класс
`Server/Replication/ReplicationLog.cs` поверх `ServerLog`, поэтому в логе сервера видны
те же метки времени и идентификаторы клиентов, что и остальные события ЛР №4.

### Требование 2. Реплицируемые данные

Реплицируется состояние общего ресурса из ЛР №3 и ЛР №4 - номер отеля и всё, что меняет
его состояние. Это данные, которые изменяются в ходе работы, имеют понятное состояние и
сверяются одной строкой.

| Таблица | Что хранит | Меняется в операции | Как проверяется совпадение |
|---|---|---|---|
| `hotels` | 2 гостиницы (справочник) | нет | сид-данные одинаковы в обеих копиях |
| `rooms` | 3 номера, `is_available` - главный ресурс | CreateBooking → FALSE, CancelBooking → TRUE | счётчик свободных + отпечаток строк |
| `guests` | 3 гостя (справочник) | нет | сид-данные одинаковы |
| `bookings` | брони, `status ∈ Created/Paid/Cancelled` | CreateBooking, PayBooking, CancelBooking | количество строк, активных строк, отпечаток |
| `payments` | платежи по брони | PayBooking | количество строк |

Совпадение копий проверяется по отпечатку (fingerprint), который сервер считает отдельно
в каждой схеме:

```
fingerprint = rooms[<id>:<is_available>|…] ; bookings[<id>/<room>/<guest>/<amount>/<status>] ; payments=<n>
```

### Требование 3. Создание Primary

Primary - это экземпляр `DatabaseInstance(InstanceRole.Primary, "riot_primary")`. При старте
сервер с флагом `--replication on`:

1. проверяет имя схемы (`HotelDatabase.IsSafeIdentifier`, шаблон `^[a-z][a-z0-9_]*$`);
2. создаёт схему, если её нет (`EnsureSchema`), затем пять таблиц и сид-данные - то же самое,
   что в ЛР №4, только в своей схеме;
3. выполняет проверку доступности (`Probe()`) и помечает экземпляр `AVAILABLE`.

Строка запуска сервера из прогона:

```
[SERVER] port=5356 reserveDelayMs=300 timeDelayMs=0 sync=lock storage=PostgreSQL → localhost:5432/hotelbooking
         transaction=True replication=on primary=riot_primary replica=riot_replica
[16:06:48.034] [SERVER] → [INSTANCE] Primary ready: localhost:5432/hotelbooking (schema riot_primary)
```

### Требование 4. Создание Replica

Replica создаётся симметрично (`riot_replica`), и сразу после инициализации Primary сервер
выполняет полную первичную синхронизацию Primary → Replica, чтобы начать эксперименты с
`Primary = Replica` (журнал `03-server-failover.log`):

```
[16:06:48.056] [SERVER] → [SYNC] START full copy Primary → Replica (source: schema 'riot_primary', target: schema 'riot_replica')
[16:06:48.073] [SERVER] → [SYNC] SUCCESS Primary → Replica — target had 3 rooms; copied 0 bookings, 0 payments, updated 3 rooms, sequences realigned
[SERVER] PostgreSQL cluster ready: Primary + Replica (replication ON)
```

Схемы разделены: у Replica свои PK, FK, CHECK и sequence, поэтому запись в Primary физически
не может "просочиться" в копию мимо механизма репликации, а копия не зависит от основной
таблицы на уровне СУБД.

### Требование 5. Определение состояния экземпляров

Состояние хранится в экземпляре как `InstanceState { Available, Unavailable }` плюс причина
отказа и время (`FailedAtUtc`). Состояние не "декларация", а результат проверки: перед тем
как открыть соединение, экземпляр отвечает на `SELECT COUNT(*) FROM rooms`.

```
[16:06:51.050] [Client] → [INSTANCE CHECK] Primary → CHECK
[16:06:51.050] [Client] → [INSTANCE CHECK] Primary → AVAILABLE (schema riot_primary, connected, rooms = 3)
[16:06:51.059] [Client] → [FAILURE] Primary → UNAVAILABLE (schema riot_primary, reason = failure injected by Client at 16:06:51)
[16:06:51.388] [Client 2] → [INSTANCE CHECK] Primary → UNAVAILABLE (schema riot_primary, connected, rooms = 3)
```

Операция `InstanceStatus` возвращает состояние обеих копий, какую из них сервер считает
служебной (`serving`) и результат сверки. Начальное штатное состояние (`01-cluster-status.log`):

```
[LR5] Primary + Replica (replication ON), serving = Primary
[LR5] Primary = AVAILABLE (schema riot_primary, connected, rooms = 3)
[LR5] Replica = AVAILABLE (schema riot_replica, connected, rooms = 3)
```

### Требование 6. Реализация репликации

Способ передачи изменений - последовательная репликация после успешного изменения Primary
(методичка это прямо допускает). Изменение подтверждено в Primary → сервер копирует
изменённые строки в Replica тем же SQL-соединением, но с другим именем схемы.

| Что реплицируется | SQL | Примечание |
|---|---|---|
| `bookings` | `INSERT INTO <target>.bookings (cols) SELECT cols FROM <source>.bookings WHERE id = ANY(@ids) ON CONFLICT (id) DO UPDATE SET …` | идемпотентно: повтор не даёт дублей |
| `payments` | тот же паттерн `INSERT … SELECT … ON CONFLICT (id) DO UPDATE` | идёт за своей бронью |
| `rooms` | `UPDATE <target>.rooms t SET is_available = s.is_available FROM <source>.rooms s WHERE s.id = t.id AND t.is_available IS DISTINCT FROM s.is_available` | состояние номера |
| sequence | `SELECT setval(pg_get_serial_sequence('<target>.<table>','id'), …)` | после полной синхронизации новые id не конфликтуют |

Журнал одной операции репликации (`02-server-replication.log`):

```
[16:06:47.736] [Client] → [INSTANCE CHECK] Primary → AVAILABLE (schema riot_primary, connected, rooms = 3)
[16:06:47.736] [Client] → [ROUTING] request is redirected to Primary (schema riot_primary) — normal operation
[16:06:47.736] [Client] → [INSTANCE WRITE] Primary → UPDATE
[16:06:47.743] [Client] → [DB] COMMIT → changes saved
[16:06:47.752] [Client] → [REPLICATION] START Primary → Replica, changed rows: bookings = [1], rooms = [101]
[16:06:47.752] [Client] → [REPLICATION] UPDATE Replica (schema 'riot_replica')
[16:06:47.776] [Client] → [REPLICATION] SUCCESS — Primary → Replica: 1 booking row(s), 0 payment row(s), 1 room row(s) copied
[16:06:47.776] [Client] → [RESULT] REPLICATION Primary → Replica: OK (rows: bookings = 1, payments = 0, rooms = 1)
[16:06:47.778] [Client] → [ROUTING] Request → SUCCESS (instance = Primary)
```

Репликацию можно выключить (`--replication off`): тогда сервер работает ровно как в ЛР №4,
режим называется `Primary only (replication OFF)`, а все операции ЛР №5 отвечают
`… is available only when the server is started with --replication on`.

## 3. Часть 3. Моделирование отказа и Failover

### Требование 1. Штатное состояние

Перед экспериментом проверено и зафиксировано (`03-server-failover.log`, первые строки):

```
[LR5] Primary = AVAILABLE (schema riot_primary, connected, rooms = 3)
[LR5] Replica = AVAILABLE (schema riot_replica, connected, rooms = 3)
```

### Требование 2. Моделирование отказа и его обнаружение

Отказ моделируется двумя способами (см. раздел 0): командой `FailInstance` от клиента-оператора
и реальной недоступностью базы копии.

```
[16:06:51.058] [Client] → START FailInstance (simulated outage)
[16:06:51.059] [Client] → [FAILURE] Primary → UNAVAILABLE (schema riot_primary, reason = failure injected by Client at 16:06:51)
[16:06:51.059] [Client] → SUCCESS Primary marked UNAVAILABLE
```

Получено требуемое состояние `Primary → UNAVAILABLE`, `Replica → AVAILABLE`.
Обнаружение отказа при обращении - на следующем же запросе клиента, аварийного завершения
сервера нет (в конце прогона `03-failover.log` отдельная проверка
`[LR5] server is still alive (operation without data) → True`).

Реальная ошибка соединения с копией, полученная проверкой (`07-replica-down.log`):

```
[LR5] Replica = UNAVAILABLE (schema riot_replica, NOT CONNECTED — cannot open PostgreSQL database
      'localhost:5432/hotelbooking-missing (schema riot_replica)':
      3D000: database "hotelbooking-missing" does not exist)
```

### Требование 3. Реализация Failover

Переключение выполняется в `InstanceCluster.Route(clientId)` перед каждым запросом: если
Primary недоступен, сервер проверяет Replica и направляет запрос в неё; при недоступной
Replica отказ объявляется невозможным (требование 5, ситуация 11).

```
[16:06:51.077] [Client 1] → [FAILOVER] START — Primary is UNAVAILABLE (failure injected by Client at 16:06:51), switching to Replica
[16:06:51.077] [Client 1] → [INSTANCE CHECK] Replica → CHECK
[16:06:51.077] [Client 1] → [INSTANCE CHECK] Replica → AVAILABLE (schema riot_replica, connected, rooms = 3)
[16:06:51.077] [Client 1] → [FAILOVER] SUCCESS — request redirected to Replica
[16:06:51.077] [Client 1] → [ROUTING] request is redirected to Replica (schema riot_replica) — after failover
```

### Требование 1. Восстановление Primary и проверка согласованности (`04-recovery.log`)

Primary восстановлен без перезапуска сервера:

```
[LR5] Primary + Replica (replication ON), serving = Replica        ← состояние на вход
[LR5] Primary = UNAVAILABLE (schema riot_primary, connected, rooms = 3)

```

Журнал восстановления на сервере (`05-server-cycle.log`):

```

```

```
[2] расхождение после отказа → DIVERGED: free rooms: Primary = 3/3, Replica = 2/3;
    bookings: Primary = 0 row(s) (active 0), Replica = 1 row(s) (active 1);
    payments: Primary = 0, Replica = 0; row fingerprints differ
[2]   · free rooms: Primary = 3/3, Replica = 2/3
[2]   · bookings: Primary = 0 row(s) (active 0), Replica = 1 row(s) (active 1)
[2]   · payments: Primary = 0, Replica = 0
[2]   · row fingerprints differ
```

Ответы на пять вопросов, которые требует методичка:

| Вопрос | Ответ по результатам эксперимента |
|---|---|
| Какие операции выполнялись во время отказа? | Чтение состояния (`DatabaseSnapshot`, `CheckAvailability`) двумя клиентами и одно изменение - `CreateBooking` номера 101 (бронь #1, гость 2, 200.00, статус Created) |

| Какая копия содержит актуальное состояние? | Replica - изменения периода отказа применены только в ней; сервер прямо отвечает: `[3] актуальная копия → Replica` |
| Каким способом восстановить согласованность? | Полная синхронизация в направлении Replica → Primary (`SynchronizeReplicas from=replica to=primary`): копирование строк `bookings`/`payments` и перенос `is_available` по всем `rooms` с выравниванием sequence |

### Требование 2. Синхронизация после восстановления

```
[4] синхронизация Replica → Primary → Synchronization Replica → Primary finished: target had 3 rooms;
    copied 1 bookings, 0 payments, updated 3 rooms, sequences realigned |
    Primary = Replica (fingerprint rooms[101:FALSE|102:TRUE|201:TRUE];bookings[1/101/2/200.00/Created];payments=0)
[5] сверка копий → Primary = Replica (fingerprint rooms[101:FALSE|102:TRUE|201:TRUE];bookings[1/101/2/200.00/Created];payments=0)
```

Контрольная операция после восстановления - ровно та пара, что приведена в методичке
(`Primary → Update`, `Replica → Replication`):

```
[6] контрольная операция после восстановления → SUCCESS: Booking #1 cancelled and room 101 released |
    REPLICATION Primary → Replica: OK (rows: bookings = 1, payments = 0, rooms = 1)
    (экземпляр = Primary, REPLICATION Primary → Replica: OK)
[7] сверка после контрольной операции → Primary = Replica
    (fingerprint rooms[101:TRUE|102:TRUE|201:TRUE];bookings[1/101/2/200.00/Cancelled];payments=0)
```

После синхронизации запросы снова обслуживает Primary (`serving = Primary`), то есть
переключение обратно (failback) выполняется без рестарта процесса. Дамп `psql` после Части 4:
в обеих схемах `101/102/201` свободны, одна бронь `1 | 101 | 2 | 200.00 | Cancelled`,
`match = t` по всем четырём позициям.

## 9. Контрольные вопросы

**1. Что такое репликация данных?**
Поддержание второй (или нескольких) копии набора данных, в которую автоматически передаются
изменения, выполненные в основной копии. В работе: после подтверждения изменения в схеме
`riot_primary` сервер копирует затронутые строки в `riot_replica`.

**2. Для чего используется репликация в распределённой системе?**
Для доступности данных при недоступности одного узла, для чтения рядом с клиентом, для георезервирования и для распределения нагрузки чтения.

**3. Чем Primary отличается от Replica?**
Primary - экземпляр, в который по умолчанию пишут; Replica - резервная копия, которая
получает изменения из Primary. У них одинаковая структура (пять таблиц, PK/FK/CHECK),
разное назначение и разное поведение при отказе: при недоступном Primary запросы
перенаправляются в Replica, и тогда в неё пишутся изменения.

**4. Что такое отказоустойчивость?**
Способность системы продолжать выполнять функции при отказе одного из компонентов.
Здесь: отказ Primary не останавливает приложение - все запросы обслуживает Replica,
сервер не завершается аварийно.

**5. Что такое Failover?**
Переключение обслуживания на резервный экземпляр при обнаружении отказа основного.
Реализован в `InstanceCluster.Route`: `Primary → CHECK`, `Primary → UNAVAILABLE`,
`Failover → START`, `Replica → CHECK`, `Replica → AVAILABLE`, `Request redirected to Replica`,
`Request → SUCCESS`.

**6. Что такое Recovery?**
Возвращение отказавшего экземпляра в состояние `AVAILABLE`. В работе - `RestoreInstance`:
проверка соединения с `riot_primary` и восстановление маршрутизации на Primary без
перезапуска сервера.

**7. Как определить доступность экземпляра данных?**
Пассивно - по состоянию, которое хранит приложение, и активно - проверкой соединения и
чтением данных (`SELECT COUNT(*) FROM rooms` в его схеме). В работе используется и то, и
другое: программный отказ меняет состояние, а `Probe()` выявляет реальную ошибку СУБД
(`3D000` в логах 07/08).

**8. Что произойдёт, если недоступны одновременно Primary и Replica?**
Переключать нечего, Failover невозможен. Приложение не падает, а возвращает клиенту
понятный текст: `both data instances are UNAVAILABLE - Primary: …; Replica: …`, событие
`FailoverImpossible`. Проверено (ситуации 4 и 11).

**9. Зачем нужна синхронизация после восстановления Primary?**
Потому что в период отказа изменения выполнялись в Replica, и Primary отстал. Без
синхронизации восстановленный Primary начал бы обслуживать клиентов устаревшими данными и
"потерял" бы бронирования периода отказа. Эксперимент: до синхронизации
`bookings: Primary = 0, Replica = 1`.

**10. Чем репликация отличается от резервного копирования?**
Резервная копия - снимок на момент времени, восстановление из него даёт откат ко всем
изменениям после снимка. Репликация - непрерывное (или по событию) воспроизведение
изменений, копия остаётся пригодной для работы. В работе копия обновляется на каждой
успешной операции, а не "по расписанию", и из неё можно отвечать на запросы.

**11. Почему репликация и отказоустойчивость - связанные, но не одинаковые понятия?**
Репликация решает задачу "данные есть в двух местах". Отказоустойчивость требует
дополнительно: обнаружения отказа, выбора живой копии, переключения маршрутизации,
обработки ошибок и восстановления согласованности. Репликация без обнаружения отказа и
Failover - это просто копия, к которой никто сам не переключается.

**12. Что такое точка отказа (Single Point of Failure)?**
Элемент архитектуры, выход которого останавливает систему целиком.

**13. Почему один Primary может являться Single Point of Failure?**
Если экземпляр единственный, его недоступность делает невозможными и чтение, и запись -
приложение остановить нечем, кроме как отказом всем клиентам. Именно этот случай моделируется
до введения Replica: запрос к недоступному Primary возвращает ошибку.

**14. Почему наличие двух копий данных не гарантирует автоматическое переключение?**
Нужны механизмы: определение состояния копии (у нас - `State` + `Probe()`), маршрутизация
запросов (`Route()`), регистрация событий и разрешение писать в резерв. Две копии "сами по
себе" не переключают клиента - переключение реализовано в коде сервера.

**15. Какие проблемы возникают при одновременном изменении нескольких реплик?**
Конфликт версий и потерянные обновления, нарушение целостности от ссылочной
независимости копий, дубли идентификаторов из разных sequence, необходимость кворума или
выбора одного источника правды. В работе проблема исключена явным правилом: пишет только
один экземпляр - `serving`, репликация однонаправленная, а синхронизация указывает
источник (`source` → `target`).

**16. Какие недостатки может иметь репликация?**
Задержка распространения изменений и чтение устаревших данных, дублирование хранения,
дополнительная нагрузка на СУБД и сеть, риск расхождения при сбое репликации, сложность
разрешения конфликтов и обратного переключения. В работе задержка устраняется последовательной моделью:
изменение в Primary подтверждено - потом копия; сбой репликации виден как
`ReplicationFailed`, а не потерян.

**17. Что произойдёт, если репликация завершится ошибкой?**
Принятое изменение в serving-экземпляре не откатывается, а событие репликации
фиксируется: `REPLICATION FAILED: InstanceUnavailableException…`, `EventTriggered =
ReplicationFailed`. Копии расходятся, расхождение обнаруживается `CompareReplicas`
(`DIVERGED`) и устраняется `SynchronizeReplicas`. Так произошло в Части 3 и в шаге [6] цикла.

**18. Как проверить, что Primary и Replica находятся в согласованном состоянии?**
Сравнить содержимое копий независимо: приложение считает отпечаток каждой схемы и сверяет
его (`Primary = Replica (fingerprint …)`), а независимо от приложения - `psql`-запросом по
двум схемам (в логах таблица `item | primary | replica | match`).

**19. Какие механизмы нужно реализовать, чтобы приложение продолжало работу при отказе одного экземпляра?**
Хранение и проверка состояния экземпляров, выбор экземпляра под каждый запрос
(маршрутизация + Failover), запись в резерв при отказе основного, регистрация событий,
обработка ошибок как результата операции, а не исключения, приводящего к падению,
восстановление экземпляра, синхронизация и сверка согласованности. Все они есть в сервере
(раздел 7) и покрыты тестами (раздел 5).

## 11. Как воспроизвести

```bash
# один раз: база должна существовать (сервер создаёт схемы сам, createdb для Replica не нужен)
createdb hotelbooking

dotnet test

# вручную: сервер с кластером и клиент
dotnet run --project Server  -- --storage postgres --replication on --port 5356 \
    --primary-schema riot_primary --replica-schema riot_replica --reserve-delay 300
dotnet run --project Client  -- --port 5356 --name "Client 1" --scenario repl
dotnet run --project Client  -- --port 5356 --name "Client 2" --scenario failover
dotnet run --project Client  -- --port 5356 --name "Client 1" --scenario recovery

# независимая проверка копий средствами СУБД
psql -d hotelbooking -c "SELECT COALESCE(p.id, r.id) AS room_id,
       p.is_available AS in_primary, r.is_available AS in_replica,
       p.is_available IS NOT DISTINCT FROM r.is_available AS match
  FROM riot_primary.rooms p FULL JOIN riot_replica.rooms r USING (id) ORDER BY 1;"
```

Пароль нигде в файлах не хранится: `libpq` берёт его из `PGPASSWORD` или `~/.pgpass`,
в строках подключения его нет. Системное время компьютера не изменялось - смещение часов
моделировалось только внутри клиента (`--offset`).
