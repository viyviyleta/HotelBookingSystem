# Лабораторная работа №7. Реализация выбора лидера и механизма консенсуса в распределенной системе

**Вариант 2. Предметная область:** бронирование отелей.
**Согласуемое состояние:** `BookingStatus` (значения из схемы базы: `Created`, `Paid`, `Cancelled`).
**Правило выбора лидера:** доступный узел с наибольшим идентификатором.
**Кластер:** 5 узлов (Node 1 - Node 5), каждый узел слушает свой TCP-порт на 127.0.0.1, все узлы живут в одном процессе сервера.
**Большинство:** `Majority = всего узлов / 2 + 1`, то есть 3 из 5. Большинство считается по всему кластеру, а не по числу живых узлов.
**Проект:** продолжение ЛР №6, клиент-серверное приложение на C# (.NET 10) + PostgreSQL.
**Рабочая директория:** `/Users/violettababich/Desktop/Univer/RIOT/HotelBookingSystem`.

Все цифры и строки журналов в отчёте переписаны из файлов `docs/logs/lr7/`, которые получены прогоном
`scripts/run_lr7_experiments.sh`. Прогон состоит из 11 шагов: каждый шаг поднимает свежий сервер со своим
кластером узлов и выполняет отдельный клиентский сценарий. Состояние таблиц предметной области дополнительно
снимается утилитой `psql` до попыток голосования и после них (`10-no-majority-proof.log`, `11-applied-proof.log`),
так что вывод «без большинства ничего не записано» проверен не журналом сервера, а базой данных.

По заданию полноценные алгоритмы Paxos, Raft и Zab не реализованы. Реализована простая модель из методички:

```
выбор лидера → обнаружение отказа → повторный выбор лидера → голосование → достижение консенсуса
```

## 0. Цель и ход работы

Цель работы - изучить принципы согласования состояния между узлами распределенной системы и получить
приложение, в котором:

1. пять узлов взаимодействуют между собой по TCP;
2. каждый узел имеет уникальный ID, состояние (`AVAILABLE` / `FAILED`) и роль (`LEADER` / `FOLLOWER`);
3. узел знает другие узлы и умеет отправлять и принимать сообщения;
4. выполняется выбор лидера по правилу «наибольший ID среди доступных»;
5. доступность узлов проверяется heartbeat, отказ обнаруживается по таймауту ответа;
6. при отказе лидера выбирается новый лидер, и лидер в кластере всегда один;
7. лидер предлагает значение, узлы голосуют `YES` / `NO`;
8. решение принимается только при наличии большинства;
9. согласованное значение `BookingStatus` записывается в базу и публикуется как событие ЛР №6;
10. смоделированы отказы одного и нескольких узлов и исследованы случаи, когда консенсус возможен и невозможен;
11. ведётся журнал работы узлов с временем, ID, состоянием, ролью, выборами, отказом, предложением, голосами и результатом;
12. механизм покрыт unit-тестами и обрабатывает десять ситуаций ошибок без аварийного завершения.

Топология распределенной системы:

```
Client ── Request{Operation, Payload} ──► ServerListener → RequestHandler
   ▲                                                    │
   │        Response{IsSuccess, Message, Data}          ▼
   └────────────────────────────────────────── DbBookingService (IConsensusBookingApi)
                                                          │
                                    PayBooking / CancelBooking → Propose(BookingStatus)
                                                          │
                                                          ▼
                                          ClusterManager (5 узлов, один процесс)
                                          │  выборы, heartbeat, голоса, COMMIT
                                          ▼
        Node 1        Node 2        Node 3        Node 4        Node 5
        5411          5412          5413          5414          5415   (TCP 127.0.0.1)
        FOLLOWER      FOLLOWER      FOLLOWER      FOLLOWER      LEADER
                                                          │
                                            консенсус (YES ≥ Majority) → применить решение
                                                          ▼
                        BookingStore → PostgreSQL riot_primary → репликация в riot_replica (ЛР №5)
                                                          │
                                                          ▼
                        EventPublisher → broker-1, broker-2 → Subscriber (ЛР №6)
```

Клиент не знает ни одного узла: он вызывает обычные операции предметной области (`PayBooking`,
`CancelBooking`) или явную команду `ProposeChange`, а кластер согласует запись. Publisher, Broker и
репликация ЛР №5-№6 не переписаны: консенсус встал перед записью, а не вместо неё.

### Состояния и роли

Состояние узла - ровно две величины из методички:

```
Node 3
Status: AVAILABLE
Role: FOLLOWER

Node 5
Status: FAILED
Role: LEADER
```

Обе комбинации видны в прогоне напрямую. Отказ текущего лидера (`silent`) помечает узел `FAILED`, но роль
до ближайших выборов остаётся `LEADER` - это строка heartbeat-обмена из `03-part3-4-failure.log`:

```
| Node 1 → Node 5 (leader check)   | HEARTBEAT | NO RESPONSE | FAILED | LEADER | 500 | 0 | node 5 did not answer within 500 ms (heartbeat timeout) |
```

Кластер не «чинит» роль автоматически: роль меняет только процедура выборов, поэтому `Status: FAILED` плюс
`Role: LEADER` - нормальное состояние системы между отказом и повторным выбором. После выборов отставший
лидер принимает победителя и переходит в `FOLLOWER`, оставаясь при этом недоступным (та же строка 38 файла
`03-part3-4-failure.log`):

```
| Node 5 | 5415     | FAILED    | FOLLOWER | SILENT | no response: node 5 did not answer within 500 ms (heartbeat timeout) | 4 | 16 | 3 | 1 | 0 | 0 | Node 5 | none |
```

`FailNode` со способом `state` отличается тем, что узел сам объявляет себя `FAILED` и сразу сбрасывает роль:
такой узел не может остаться «лидером в отказе».

### Способы смоделировать отказ

Методичка требует уметь моделировать отказ четырьмя способами. В работе к ним добавлен пятый -
`offline` (остановка сокет-слушателя), потому что Требование 2 отдельно называет ситуацию
«невозможность связаться с узлом», а она возможна только при закрытом порте.

| Способ | Значение `--mode` | Что делает узел | Как это видит кластер |
|---|---|---|---|
| изменением состояния | `state` | `DeclareFailed`: состояние `FAILED`, роль `FOLLOWER` | `Node 4 already FAILED` |
| остановкой обработки | `stalled` | соединение принимает, сообщение не обрабатывает никогда | `Node 1 NO RESPONSE` |
| искусственным исключением | `exception` | при обработке сообщения бросает `NodeProcessingException` | `Node 2 REFUSED` |
| прекращением ответа на heartbeat | `silent` | отвечает на обычные сообщения, молчит на `HEARTBEAT` и `ELECTION` | `Node 5 NO RESPONSE` |
| выключенным процессом | `offline` | `ClusterNodeHost.Stop()`: слушатель закрыт | `Node 3 UNREACHABLE` |

Проверка всех способов одним прогоном (`03-part3-4-failure.log`):

```
    mode stalled    → Node 1 → STALLED (node stopped processing messages) | проверка: HEARTBEAT round: exchanges = 5, answered = 4, failures detected = 1 → Node 1 NO RESPONSE
    mode exception  → Node 2 → EXCEPTION (artificial exception while handling a message) | проверка: HEARTBEAT round: exchanges = 5, answered = 4, failures detected = 1 → Node 2 REFUSED
    mode offline    → Node 3 → OFFLINE (node process is down, listener stopped) | проверка: HEARTBEAT round: exchanges = 5, answered = 4, failures detected = 1 → Node 3 UNREACHABLE
    mode state      → Node 4 → STATE (node state changed to FAILED) | проверка: HEARTBEAT round: exchanges = 5, answered = 4, failures detected = 1 → Node 4 already FAILED
```

### Обмен сообщениями между узлами

Протокол сообщений использует тот же транспорт, что и ЛР №4-№6: TCP, JSON по одному сообщению на строку.
Конверт - `Request` / `Response` из `Shared.Network`, где поле `Operation` несёт тип сообщения, `ClientName` -
имя узла-отправителя, а `Payload` - JSON тела `ClusterMessage`.

```csharp
public Request ToRequest() => new()
{
    Operation = Type,
    ClientName = From > 0 ? $"Node {From}" : "Cluster",
    Payload = JsonSerializer.Serialize(this)
};
```

Виды сообщений (запросы узел принимает и на них отвечает, ответы узел только отправляет):

| Тип | Разряд | Назначение | Кто отвечает |
|---|---|---|---|
| `HEARTBEAT` | запрос | проверка доступности узла | `ALIVE` с состоянием и ролью |
| `ELECTION` | запрос | опрос перед выбором лидера | `ALIVE` (готов участвовать) или `NO RESPONSE` |
| `LEADER` | запрос | объявление результата выборов | `ALIVE` с `role = FOLLOWER` |
| `PROPOSE` | запрос | предложение значения | `VOTE` (`YES` / `NO` / отказ) |
| `COMMIT` | запрос | сообщение согласованного значения | `ALIVE` («узел запомнил значение») |
| `STATUS` | запрос | отчёт о состоянии узла | `ALIVE` с полным состоянием |
| `ALIVE` | ответ | подтверждение живости | не обрабатывается как запрос |
| `VOTE` | ответ | голос | не обрабатывается как запрос |

Разделение на запросы и ответы нужно для обработки ошибок: рассылка `ALIVE` всем узлам отклоняется
как бессмысленная, а узел, получивший тело не своего адреса, отвечает текстом ошибки, а не падает
(`ClusterNodeHost.Process` возвращает `null` для «молчания» и держит соединение открытым - так отправитель
и получает таймаут, а не мгновенный пустой ответ).

Параллельная рассылка сообщений нескольким узлам сразу (`06-errors.log`, ситуация 9):

```
        broadcast                                    → SUCCESS: parallel STATUS from Node 5 to 4 node(s): Node 1 = AVAILABLE, Node 2 = AVAILABLE, Node 3 = FAILED, Node 4 = AVAILABLE
```

## 2. Часть 2. Реализация выбора лидера

Правило: лидером становится доступный узел с максимальным ID. Процедура `ClusterManager.Elect(reason, clientId)`:

1. в журнале фиксируется `Election started (reason: ...)`;
2. инициатор рассылает `ELECTION` всем узлам параллельно (`Task.WhenAll`) и ждёт ответы до таймаута;
3. по каждому узлу в журнал пишется строка `Node N AVAILABLE (role FOLLOWER, knows 4 peer(s))` или
   `Node N NO RESPONSE → excluded (...)`;
4. среди ответивших и доступных выбирается узел с наибольшим ID;
5. победитель получает роль `LEADER`, остальным рассылается `LEADER`-объявление, и каждый подтверждает
   `Node N accepted Node M as the only leader`;
6. если объявление услышал узел, который уже считает себя лидером, он возвращается в роль `FOLLOWER` -
   так в кластере не может быть двух лидеров.

Результат выбора записан в журнал (Требование Части 2) - строки
из `02-part1-2-nodes.log`:

```

| 17:55:42.864 | Node 1  | ELECTION | Node 1 AVAILABLE (role FOLLOWER, knows 4 peer(s))                              |
| 17:55:42.864 | Node 2  | ELECTION | Node 2 AVAILABLE (role FOLLOWER, knows 4 peer(s))                              |
| 17:55:42.864 | Node 3  | ELECTION | Node 3 AVAILABLE (role FOLLOWER, knows 4 peer(s))                              |
| 17:55:42.864 | Node 4  | ELECTION | Node 4 AVAILABLE (role FOLLOWER, knows 4 peer(s))                              |
```

## 3. Часть 3. Обнаружение отказа лидера

Отказ моделировался на реальном лидере: `Node 5 → LEADER`, затем `FailNode(5, "silent", ...)`.
Проверка доступности - heartbeat между узлами (`HeartbeatProbe`): лидер опрашивает всех последователей,
а затем последователь `Node 1` опрашивает самого лидера. Именно эта обратная проверка и обнаруживает отказ.

До отказа (`03-part3-4-failure.log`):

```
[2] heartbeat до отказа → HEARTBEAT round: exchanges = 5, answered = 5, failures detected = 0 → every node is alive
| Node 1 → Node 5 (leader check)   | ALIVE | ALIVE | AVAILABLE | LEADER | 0 | 4 | Node 5 ALIVE, role LEADER, knows 4 peer(s) |
```

После отказа лидера:


### Связь консенсуса с предметной областью (вариант 2)


## 11. Связь реализованного механизма с Paxos, Raft и Zab

Таблица соответствия из теоретической части и то, чем именно реализован каждый элемент:

| Лабораторная | Реальные алгоритмы | Что в этой работе |
|---|---|---|
| Node | Участник распределенной системы | `ClusterNode` со своим TCP-портом |
| Leader | Leader / координатор | `NodeRole.Leader`, максимум ID среди доступных |
| Leader Election | Выбор лидера | `ELECTION`-опрос + `LEADER`-объявление |
| Vote | Голосование | `PROPOSE` → `VOTE` (`YES` / `NO`) |
| Majority | Quorum | `Total / 2 + 1` по всему кластеру |
| Agreement | Согласованное решение | `CONSENSUS ACHIEVED` + `COMMIT` |
| Node Failure | Отказ узла | пять способов отказа + heartbeat-обнаружение |
| New Leader | Повторный выбор лидера | `Elect` после потери лидера |

**Raft.** Реализация ближе всего к Raft: явные роли (Leader / Follower), выбор лидера, heartbeat как
механизм поддержания власти лидера, кворум для решения и рассылка согласованного значения (`COMMIT` ≈
`AppendEntries`). Отличия: в Raft лидер выбирается голосованием с таймаутами и терминами (term), а здесь
победитель определяется детерминированно - наибольшим ID; журнал Raft упорядочен и реплицируется, а
здесь `COMMIT` только сообщает значение.

**Paxos.** Paxos решает задачу согласования значения без постоянного лидера: акторные роли (proposer,
acceptor, learner), две фазы (`prepare` / `promise`, `accept`), победителем становится предложение с
наименьшим номером раунда. В работе есть общие с Paxos элементы - предложение с идентификатором раунда
(`P1`, `P2`), голоса участников, кворум, отказ устаревшего предложения - но нет двухфазности: голос
и применение идут в один раунд, а координирует процесс лидер.

**Zab.** ZooKeeper Atomic Broadcast согласует не одно значение, а порядок изменений и обеспечивает
двойное большинство: кворум при выборах и кворум при записи каждого предложения. В работе используется
только одно большинство (на голосование), выборы не требуют второго кворума, а порядок изменений
задаётся сериализацией раундов семафором в одном процессе.

**Что общего.** Во всех трёх алгоритмах решение принимается только при кворуме, отказ лидера приводит к
новым выборам, а система остаётся работоспособной при потере части узлов - ровно то, что проверяют
четыре эксперимента Части 6.

## 13. Контрольные вопросы

**1. Что такое консенсус?**
Процесс, при котором несколько узлов распределенной системы приходят к одному общему решению - например,
какой узел является лидером или какое значение состояния считать актуальным. В работе консенсус фиксируется
строкой `CONSENSUS ACHIEVED` и означает, что не менее `Majority` узлов согласовали одно значение.

**2. Для чего необходим консенсус в распределенной системе?**
Без него узлы принимают решения независимо, и состояние системы становится противоречивым: разные узлы
считают актуальными разные значения, а клиент получает несогласованные ответы. Консенсус даёт единственное
решение, которое выживает после отказа части узлов.

**3. Что такое Leader?**
Узел, которому поручена координация: он координирует выборы, распространяет информацию, предлагает
изменения состояния и инициирует принятие решений. В работе лидер координирует `PROPOSE`, подсчитывает
голоса и объявляет результат. Лидер - не единственный работоспособный узел: при его выходе из строя
система выбирает нового.

**4. Что такое Follower?**
Узел без права предлагать решение: он получает сообщения, отвечает на heartbeat, участвует в выборах,
принимает предложение, отдаёт голос и сообщает о своём состоянии. Все пять узлов в старте - `FOLLOWER`,
кроме победителя выборов.

**5. Что такое Leader election?**
Процесс определения узла, который будет лидером. В работе используется простое правило: доступный узел
с наибольшим ID. Процедура опрашивает узлы по TCP (`ELECTION`), исключает не ответившие и объявляет
победителя (`LEADER`-сообщение всем доступным).

**6. Что происходит при отказе лидера?**
Heartbeat-проверка получает `NO RESPONSE` по таймауту, узел помечается `FAILED`, лидер в кластере
аннулируется, следующая процедура выборов выбирает нового - в эксперименте `Node 5 → Node 4`. Голосование
в это время не блокируется безвозвратно: после выборов оно продолжается с новым лидером.

**7. Для чего используется Heartbeat?**
Как механизм обнаружения доступности: `Node 1 → Node 5: HEARTBEAT?`, ответ `ALIVE` означает «узел жив»,
отсутствие ответа в пределах таймаута означает «узел недоступен». В работе heartbeat - реальное TCP-соединение
с таймаутом чтения 500 мс.

**8. Как определить, что узел недоступен?**
По итогу опроса: `NO RESPONSE` (не ответил за таймаут), `UNREACHABLE` (соединение отклонено - слушатель
закрыт), `REFUSED` (исключение при обработке), `already FAILED` (узел сам объявил себя failed). Первые два
способа - настоящие сетевые признаки, последние два - явное состояние узла.

**9. Что такое Majority?**
Минимальное число узлов, согласие которого достаточно для решения: `всего узлов / 2 + 1`. Для пяти узлов
это 3, для четырёх тоже 3. Важно, что большинство считается по всему кластеру, а не по числу живых узлов:
при 2 живых из 5 большинство недостижимо, хотя 2 из 2 - это больше половины живых.

**10. Что такое голосование в распределенной системе?**
Рассылка предложения всем доступным узлам и сбор их ответов. В работе это `PROPOSE` → `VOTE`, голоса
считаются по раунду (`P1`, `P2`), итоги: `YES`, `NO`, `NO RESPONSE`, `REFUSED`.

**11. Что произойдёт, если голоса разделились поровну?**
При чётном числе узлов равенство голосов не даёт большинства, решение не принимается. При нечётном кластере
из пяти узлов равного деления `YES/NO` не бывает: максимум при разделении это `YES = 2`, `NO = 3` - и
консенсуса нет, либо `YES = 3` - и консенсус есть. В эксперименте с разделением `YES = 3`, `NO = 2`
решение принято, потому что большинства требует `YES`, а не «меньшинство».

**12. Почему наличие лидера само по себе не гарантирует консенсус?**
Лидер только предлагает и считает голоса. Решение требует кворума ответов: при живых двух узлах из пяти
лидер `Node 5` есть, но `YES = 2 < Majority = 3`, и кластер отвечает `CONSENSUS NOT ACHIEVED`. Лидер также
может отстать от реальности (потерять кворум между двумя своими предложениями), поэтому кворум проверяется
в каждом раунде заново.

**13. Чем выбор лидера отличается от достижения консенсуса?**
Выбор лидера отвечает на вопрос «кто координирует» и использует опрос доступности. Консенсус отвечает на
вопрос «какое значение принять» и использует голоса по конкретному предложению. Первая процедура может
успешно завершиться и при отсутствии большинства для записи (выбрать лидера можно из двух узлов), но вторая
в этот момент неизбежно откажет.

**14. Что такое отказ узла?**
Ситуация, когда узел не участвует в работе механизма: не меняет состояние, не отвечает, не голосует.
Отказ бывает явным (узел объявил `FAILED`), молчанием (таймаут heartbeat), ошибкой обработки (исключение)
и полной недоступностью (закрытый порт).

**15. Что такое Paxos?**
Алгоритм консенсуса без постоянного лидера: proposer готовит предложение с номером раунда, acceptor-ы
обещают не принимать предложения с меньшим номером (`prepare` / `promise`), затем значение принимается при
кворуме на фазе `accept`, а learner-ы узнают результат. Решает ту же задачу - согласовать одно значение при
отказах.

**16. Что такое Raft?**
Алгоритм консенсуса с явным лидером: узлы - follower / candidate / leader, лидер выбирается голосованием с
кворумом и удерживается heartbeat-ами, журнал операций реплицируется от лидера к большинству. Из трёх
алгоритмов работа ближе всего к Raft, так как в ней те же роли, выборы, heartbeat и кворум для решения.

**17. Что такое Zab?**
Алгоритм атомарного вещания в Apache ZooKeeper: согласует порядок изменений, а не одно значение, и требует
двух кворумов - при выборах лидера и при записи каждого предложения. Обеспечивает linearizability и
двойное большинство, чего учебная реализация с одним кворумом не гарантирует.

   узел переходит в `FAILED`, кластер остаётся без лидера и выбирает `Node 4`.
4. Повторный выбор сохраняет инвариант «лидер ровно один» - проверено прогоном

5. Голосование и консенсус реализованы для состояния варианта: `BookingStatus=Paid` согласован шестью
   раундами в разных экспериментах, `YES = 5 / 4 / 3` при `Majority = 3` даёт `CONSENSUS ACHIEVED`, а
   `YES = 2` - отказ.
6. Все четыре эксперимента Части 6 совпали с ожидаемым результатом: 5/5, 4/5 и 3/5 → `CONSENSUS ACHIEVED`,
   2/5 → `CONSENSUS NOT ACHIEVED`; колонка «Совпадает» во всех строках равна «да».
7. Большинство считается по всему кластеру, а не по числу живых узлов. Это ключевой момент: 2 живых узла из 5
   - формально больше половины живых, но `Majority = 3`, поэтому решение не принимается.
8. Связь с предметной областью доказана независимой проверкой: `psql`-снимок показывает `status = Created` и
   `payments = 0` после двух отказанных попыток и `status = Paid`, `payments = 1` после консенсуса.
9. Реализованы пять способов моделирования отказа: `state`, `stalled`, `exception`, `silent`, `offline`. Все

   методички.
10. Десять ситуаций ошибок Требование 2 обработаны как ожидаемые результаты, плюс восемь ошибочных команд

11. Журнал кластера содержит все элементы, перечисленные в Требовании 1: время, ID, состояние, роль, начало

### Ограничения учебной реализации

1. Все пять узлов живут в одном процессе сервера. Отказ узла моделируется состоянием, молчанием, исключением
   или остановкой слушателя, но не убийством реального процесса, поэтому «потеря памяти» и разделение часов
   между узлами в работе не проверяются.
2. Лидер выбирается детерминированно по максимальному ID, а не голосованием с терминами и таймаут-избирателями,
   поэтому кластер не переживает «split-brain» между двумя половинами сети: разделения сети здесь просто нет,
   все соединения - к 127.0.0.1.
3. Голосование однофазное: предложение и применение идут в одном раунде. В Paxos и Raft есть отдельная фаза
   обещания или журнал терминов, который не позволяет старому лидеру записать значение после начала новых
   выборов. Здесь от частичной потери кворума защищает только повторная проверка `Majority` в каждом раунде.
4. `COMMIT` доставляется доступным узлам без подтверждения доставки и без повторных попыток: узел, который
   молчал на момент рассылки, узнает согласованное значение только на следующем `STATUS`-опросе.
5. Журнал кластера - кольцевой буфер в памяти (400 записей) и не переживает перезапуск сервера; история
   выборов и голосований сохраняется только в файлах лога прогона `docs/logs/lr7/`.
6. Единственное значение, согласуемое с предметной областью, - `BookingStatus` брони. Запись бронирования
   (`CreateBooking`) остаётся прямой операцией, как в ЛР №4-№6: по условию методички достаточно согласовать
   изменение состояния.
7. Большинство считается по числу узлов, но не по их весу и не по очереди раундов, поэтому два параллельных

   предложений.
