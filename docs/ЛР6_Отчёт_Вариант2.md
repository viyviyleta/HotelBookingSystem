## 0. Цель и ход работы

Цель работы - изучить модель Publish/Subscribe и получить приложение, в котором:

1. сервер формирует событие предметной области;
2. Publisher передаёт событие Broker-у;
3. Broker хранит подписки, определяет получателей и доставляет событие подписчикам;
4. один Subscriber получает только интересующие его типы событий;
5. подписчики обрабатывают события независимо и асинхронно;
6. отказ одного Subscriber не останавливает остальных и не роняет сервер;
7. новый Subscriber подключается без изменения Publisher;
8. события временно хранятся в очереди Broker-а и доставляются повторно;
9. добавлен AnalyticsService, который собирает статистику и не меняет данные предметной области;
10. проверена работа нескольких клиентов и нескольких Broker-ов.

| Часть | Что выполняется | Где доказательство |
|---|---|---|
| 1 | Базовая модель Pub/Sub: Event, Publisher, Broker, Subscriber, подписка, доставка | раздел 1, `02-part1-basic.log`, `02-server-part1.log` |
| 2 | Несколько Subscriber, несколько типов событий, фильтрация, журнал | раздел 2, `03-part2-subscribers.log`, `03-server-part2.log` |
| 3 | Асинхронная обработка, искусственные задержки, отказ Subscriber, очередь | раздел 3, `04-part3-failure.log`, `04-server-part3.log` |
| 4 | Новый Subscriber, сравнение с прямым взаимодействием, полный цикл, тесты, ошибки | разделы 4, 6, 7; `05-part4-new-subscriber.log`, `06-part4-cycle.log`, `08-part4-errors.log` |
| 5 | Несколько Broker, очередь, повторная доставка, AnalyticsService, несколько клиентов, задержки | раздел 5, `07-part5-brokers.log`, `09-final-cycle.log`, `10-two-clients.log` |
| Итог | Проверка данных предметной области до и после событий | `11-domain-data-proof.log` |

Топология механизма событий:

```
Client
  │  Request{Operation, Payload}  /  Response{IsSuccess, Message, Data, EventTriggered}
  ▼
ServerListener → RequestHandler → DbBookingService (IPubSubBookingApi)
                                     │
                                     │  успешная операция с данными
                                     ▼
                              EventPublisher
                              │             │
                              ▼             ▼
                         broker-1        broker-2
                         ├ Logger        └ AnalyticsService
                         ├ RoomService
                         └ NotificationService
                              │
                              │  ошибка доставки
                              ▼
                         очередь Broker
                         PendingDelivery
                              │  RetryPending
                              ▼
                         Subscriber
```

Сервер знает Publisher и Broker-ы, но не знает состава подписчиков. Publisher знает только
список `EventBroker` и не содержит ни одного обращения к `ISubscriber`. Подписчик зарегистрирован
на своём Broker-е и знает только типы событий, на которые подписан.

## 1. Часть 1. Реализация базовой модели Pub/Sub

### Требование 1. Подготовка проекта

Проект ЛР №5 сохранён: те же клиент-серверное приложение по TCP с JSON-сообщениями, разделитель
`\n`, операции `CheckAvailability`, `CreateBooking`, `PayBooking`, `CancelBooking`, работа с
PostgreSQL через схемы `riot_primary` и `riot_replica`, транзакции, режимы `sync=lock/none` и
журнал `[HH:mm:ss.fff] [Клиент] → событие`.

Механизм Pub/Sub добавлен отдельным слоем:

| Что сохранено | Что добавлено |
|---|---|
| Операции бронирования, оплаты и отмены | Формирование событий после успешной операции |
| Транзакции и блокировки ЛР №4 | Publisher, Broker, Subscriber и очередь доставки |
| Репликация Primary → Replica ЛР №5 | Журнал публикации и доставки |
| Клиентские сценарии ЛР №4 и ЛР №5 | 9 сценариев Pub/Sub и 13 проверок ошибок |

При `--pubsub off` создаётся `DbBookingService` с `hub = null`, и поведение сервера совпадает
с ЛР №5: операции с данными работают, события не публикуются. Это проверяет тест:

```
DbBookingService_WithoutPubSub_BooksRoomsAndExplainsMissingEventOperations
```

Он подтверждает, что бронирование выполняется, а операция `PubSubStatus` возвращает понятное
сообщение о необходимости включить `--pubsub on`, а не падает.

### Требование 2. Создание модели Event

Модель события находится в `Server/Messaging/EventContracts.cs`:

```csharp
public enum EventType
{
    BookingCreated,
    BookingCancelled,
    PaymentCompleted
}

public sealed record DomainEvent(
    string EventId,
    EventType EventType,
    int EntityId,
    DateTime Timestamp,
    string ClientId,
    IReadOnlyDictionary<string, string> Data);
```

| Поле | Назначение | Пример из журнала |
|---|---|---|
| `EventId` | Идентификатор события, генерируется как `E1`, `E2`, ... | `BookingCreated #E1` |
| `EventType` | Тип события, он же идентификатор подписки | `BookingCreated` |
| `EntityId` | Идентификатор объекта предметной области | `entity = 1`, `entity = 101` |
| `Timestamp` | Время создания события | `time = 19:27:00.348` |
| `ClientId` | Клиент, по чьей операции возникло событие | `client = Client`, `client = Client A` |
| `Data` | Дополнительные данные для подписчиков | `room = 101, guest = 1, total = 200.00` |

Создание и проверка события выполняются фабрикой `DomainEventFactory`:

- `Create` заполняет тип, `EntityId`, время, клиента и копию данных;
- `NextEventId` выдаёт уникальный идентификатор `E1`, `E2`, ...;
- `IsValid` отвергает событие с неположительным `EntityId` и неизвестным типом.

Пример события из журнала `03-server-part2.log`:

```
[19:27:00.350] [Client] → [EVENT] Server → BookingCreated (room = 101, guest = 1, total = 200.00, status = Created, instance = Primary, transaction = COMMIT)
```

Событие описывает уже произошедший факт: бронь создана, оплата сохранена, бронь отменена.
Подписчик не командует сервером, а реагирует на факт.

### Требование 3. Реализация Publisher

Publisher находится в `Server/Messaging/EventPublisher.cs`. Он принимает событие от сервера и
передаёт его всем Broker-ам. Единственное поле, с которым он работает, - список Broker-ов:

```csharp
private readonly IReadOnlyList<EventBroker> _brokers;
```

| Обязанность Publisher | Как реализована |
|---|---|
| Получить событие | `Publish(DomainEvent, clientId)` вызывает `DbBookingService.Publish` |
| Передать событие Broker | `broker.Accept(domainEvent, clientId)` в цикле по `_brokers` |
| Получить результат публикации | `PublicationResult` с `IsSuccess`, `AcceptedBy`, `RefusedBy` |
| Зарегистрировать ошибку публикации | `PubSubLog.PublisherFailed` и счётчик `FailedPublications` |
| Не обращаться к Subscriber | В классе нет ни одного обращения к `ISubscriber` |

Если один Broker недоступен, Publisher публикует событие в остальные и добавляет отказ в
`RefusedBy`. Если недоступны все Broker-ы, возвращается `IsSuccess = false` с понятным текстом,
а сервер продолжает работу. Это проверяют тесты:

```
EventPublisher_Publish_WhenOneBrokerIsDown_PassesEventToTheLivingOne
EventPublisher_Publish_WhenNoBrokerIsUp_ReportsFailureInsteadOfThrowing
EventPublisher_DependsOnBrokersOnly_SoNewSubscribersChangeNothingInThePublisher
```

### Требование 4. Реализация Broker

Broker находится в `Server/Messaging/EventBroker.cs`. Он хранит подписки, определяет
получателей и доставляет событие каждому подписчику в отдельной задаче `Task.Run`.

| Обязанность Broker | Метод или механизм | Доказательство |
|---|---|---|
| Принимать события | `Accept` | `[BROKER broker-1] EVENT RECEIVED BookingCreated #E1, subscribers = 3` |
| Хранить список подписчиков | `_subscriptions`, `Register` | `[SUBSCRIBER] Logger → REGISTERED on Broker broker-1` |
| Хранить типы событий | `Registration.Types`, `Subscribe` | `[SUBSCRIBE] Logger → Subscribe(BookingCreated, BookingCancelled, PaymentCompleted)` |
| Определять получателей | `RecipientsOf(EventType)` | `[BROKER broker-1] → Logger`, `→ RoomService`, `→ NotificationService` |
| Передавать событие | `StartDelivery` → `DeliverOnce` | `[Logger] SUCCESS BookingCreated #E1 (1000 ms): ...` |
| Обрабатывать ошибки доставки | `try/catch` в `DeliverOnce`, `DeliveryOutcome` | `[RoomService] UNAVAILABLE ...`, `[Logger] CONNECTION ERROR ...` |
| Продолжать работу при отказе Subscriber | Отдельная задача на каждого получателя | остальные подписчики получают `SUCCESS` |
| Временно хранить неотданное событие | `_pending`, `PendingDelivery`, `RetryPending` | `[QUEUE broker-1] QUEUED ... kept in the broker queue` |

Ошибки доставки различаются по типу:

| Исключение | Результат в журнале |
|---|---|
| `SubscriberUnavailableException` | `UNAVAILABLE` |
| `SubscriberConnectionException` | `CONNECTION ERROR` |
| `SubscriberProcessingException` | `PROCESSING ERROR` или `FAIL` |

Broker не завершает работу при ошибке одного подписчика: запись о доставке сохраняется,
событие попадает в очередь, остальные получатели продолжают обработку.

### Требование 5. Регистрация Subscriber

Подписка реализована командой клиента `SubscribeEvent` и методом
`EventBroker.Subscribe(subscriber, types, clientId)`. После подписки Broker хранит пару
«подписчик → множество типов событий».

Журнал регистрации и подписок из `01-server-topology.log`:

```
[19:26:47.619] [SERVER] → [SUBSCRIBER] Logger → REGISTERED on Broker broker-1 (kind = logger, delay = 1000 ms)
[19:26:47.623] [SERVER] → [SUBSCRIBE] Logger → Subscribe(BookingCreated, BookingCancelled, PaymentCompleted) on Broker broker-1
[19:26:47.623] [SERVER] → [SUBSCRIBER] RoomService → REGISTERED on Broker broker-1 (kind = room, delay = 3000 ms)
[19:26:47.623] [SERVER] → [SUBSCRIBE] RoomService → Subscribe(BookingCreated) on Broker broker-1
[19:26:47.623] [SERVER] → [SUBSCRIBER] NotificationService → REGISTERED on Broker broker-1 (kind = notification, delay = 2000 ms)
[19:26:47.623] [SERVER] → [SUBSCRIBE] NotificationService → Subscribe(BookingCreated, PaymentCompleted) on Broker broker-1
[19:26:47.623] [SERVER] → [SUBSCRIBER] AnalyticsService → REGISTERED on Broker broker-2 (kind = analytics, delay = 800 ms)
[19:26:47.623] [SERVER] → [SUBSCRIBE] AnalyticsService → Subscribe(BookingCreated, BookingCancelled, PaymentCompleted) on Broker broker-2
```

Повторная подписка на тот же тип не создаёт дубликат: `Subscribe` добавляет только новые типы,
а команда `SubscribeEvent` для уже существующей подписки возвращает
`Logger was already subscribed to BookingCreated on broker-1` (ситуация 13 в разделе 7).

### Требование 6. Проверка базовой доставки

Эксперимент `pubsub-basic` (`02-part1-basic.log`) публикует `BookingCreated #E1` с
`entity = 101`:

```
[1] Client → PublishEvent BookingCreated (entity 101)
[2] Server → Event, Publisher → Broker, Broker → Subscriber → BookingCreated #E1 published to broker-1 → 3 subscriber(s), broker-2 → 1 subscriber(s)
[3] ответ сервера: IsSuccess = True, EventTriggered = BookingCreated
[4] BookingCreated #E1: публикация 1 мс, все подписчики завершились через 3004 мс
[5] Broker broker-1 → Logger → SUCCESS (1003 мс): journal record: BookingCreated #E1, entity = 101, client = Client, time = 19:26:53.825
[5] Broker broker-1 → NotificationService → SUCCESS (2002 мс): notification to guest 1: booking 101 of room 101 is confirmed, total = 200.00
[5] Broker broker-1 → RoomService → SUCCESS (3002 мс): RoomService register: room 101 → BUSY (booking 101)
[5] Broker broker-2 → AnalyticsService → SUCCESS (805 мс): analytics: BookingCreated = 1, clients = 1
[6] событие получил(а): Logger, NotificationService, RoomService, AnalyticsService, Broker принял = accepted by broker-1 → 3 subscriber(s), broker-2 → 1 subscriber(s)
```

| Подписчик | Broker | Результат | Время обработки |
|---|---|---|---|
| `Logger` | `broker-1` | `SUCCESS` | 1003 мс |
| `NotificationService` | `broker-1` | `SUCCESS` | 2002 мс |
| `RoomService` | `broker-1` | `SUCCESS` | 3002 мс |

подписчика - около 3 секунд. Это и есть независимая асинхронная обработка.

## 2. Часть 2. Несколько подписчиков и событий

### Требование 1. Создание нескольких Subscriber

В проекте четыре подписчика по умолчанию, то есть больше требуемых трёх:

| Subscriber | Broker | Назначение | Задержка | Что делает |
|---|---|---|---|---|
| `Logger` | `broker-1` | журналирование | 1000 мс | пишет тип, `EntityId`, клиента и время события |
| `RoomService` | `broker-1` | деловой подписчик варианта 2 | 3000 мс | по `BookingCreated` отмечает номер `BUSY` в собственном реестре |
| `NotificationService` | `broker-1` | уведомления | 2000 мс | формирует уведомление гостю о брони и оплате |
| `AnalyticsService` | `broker-2` | аналитика | 800 мс | считает события по типам и клиентам, данные не меняет |

`RoomService` не обращается к базе данных: он строит состояние номера из событий. Класс умеет
обрабатывать `BookingCreated` (номер становится `BUSY`) и `BookingCancelled` (номер снова `FREE`),
но в топологии варианта он подписан только на `BookingCreated`, поэтому в экспериментах номер
переходит в `BUSY`. Это отдельный подписчик предметной области, а не второй доступ к `bookings`.

### Требование 2. Подписка на события

Подписки заданы в `SubscriberFactory.DefaultSubscriptions` и совпадают с вариантом 2:

| Subscriber | `BookingCreated` | `BookingCancelled` | `PaymentCompleted` |
|---|---:|---:|---:|
| `Logger` | да | да | да |
| `RoomService` | да | нет | нет |
| `NotificationService` | да | нет | да |
| `AnalyticsService` | да | да | да |

Журнал подписок приведён в разделе 1, Требование 5. Подписка хранится в Broker-е, а не в
Publisher-е и не в серверной бизнес-логике.

### Требование 4. Разные типы событий

В работе три типа событий:

| Тип | Когда возникает | Кто получает |
|---|---|---|
| `BookingCreated` | успешно создана бронь и номер занят | `Logger`, `RoomService`, `NotificationService`, `AnalyticsService` |
| `PaymentCompleted` | успешно сохранена оплата по брони | `Logger`, `NotificationService`, `AnalyticsService` |
| `BookingCancelled` | успешно отменена бронь и номер освобождён | `Logger`, `AnalyticsService` |

Проверка фильтрации из `03-part2-subscribers.log`:

```
[LR6] BookingCreated #E1: получили = Logger, NotificationService, RoomService, AnalyticsService, не получили =
[LR6] PaymentCompleted #E2: получили = Logger, NotificationService, AnalyticsService, не получили = RoomService
[LR6] BookingCancelled #E3: получили = Logger, AnalyticsService, не получили = NotificationService, RoomService
[LR6] типов событий в эксперименте: BookingCreated, PaymentCompleted, BookingCancelled (по заданию нужно не менее трёх)
```

`RoomService` не получает `PaymentCompleted`, потому что оплата не меняет занятость номера.

### Требование 2. Сравнение прямого взаимодействия и Pub/Sub

Таблица из `05-part4-new-subscriber.log`:

| Критерий | Прямое взаимодействие | Pub/Sub |
|---|---|---|
| какие компоненты знают друг о друге | Сервер знает каждый компонент и вызывает его напрямую: `Logger`, `RoomService`, `NotificationService` по типам и именам | Сервер знает `Publisher` и `Broker`; `Publisher` не знает ни одного `Subscriber` |
| где находится логика маршрутизации | В сервере: список вызовов зашит в код каждой операции | В `Broker`: получатели выбираются по таблице подписок |
| насколько легко добавить новый компонент | Нужно править сервер и пересобирать все операции | Достаточно зарегистрировать `Subscriber` и подписку: `Publisher` и сервер не меняются |
| что произойдёт при отказе одного `Subscriber` | Операция падает или ждёт таймаута, остальные компоненты не получают вызов | `Broker` фиксирует ошибку доставки, остальные `Subscriber` работают, событие ждёт в очереди |
| насколько сильно связаны компоненты | Сильная связь: сервер компилируется со всеми компонентами | Слабая связь (`Loose coupling`): общий контракт - только `Event` |

В Pub/Sub добавление `AuditService` не потребовало изменений ни в `EventPublisher`, ни в
бизнес-операциях `CreateBooking`, `PayBooking`, `CancelBooking`. Достаточно было команды
`AddSubscriber` и `SubscribeEvent`.

## 5. Часть 5. Работа с несколькими Broker

### Требование 1. Несколько Broker

В проекте два Broker-а:

| Broker | Подписчики | Роль в эксперименте |
|---|---|---|
| `broker-1` | `Logger`, `RoomService`, `NotificationService`, при необходимости `AuditService`, `ReportService` | основная группа подписчиков предметной области |
| `broker-2` | `AnalyticsService` | отдельная группа аналитики |

Зачем нужны несколько Broker-ов:

1. разделить подписчиков по группам и не смешивать деловую обработку с аналитикой;
2. распределить нагрузку: у каждого Broker-а своя очередь и свои задачи доставки;
3. локализовать отказ: недоступность `broker-1` не мешает `broker-2` принять событие;
4. упростить добавление новых групп подписчиков без изменения Publisher-а.

Что происходит при отказе одного Broker-а (`07-part5-brokers.log`):

```
[9] отказ одного Broker → Broker broker-1 is UNAVAILABLE: broker process stopped
    событие всё равно опубликовано через живой Broker → PaymentCompleted #E6 published to broker-2 → 1 subscriber(s); refused by broker-1 (broker 'broker-1' is UNAVAILABLE: ...)
    принят: accepted by broker-2 → 1 subscriber(s), доставка = AnalyticsService
[10] Broker восстановлен → Broker broker-1 is AVAILABLE again
     итог: brokers = 2 (broker-1: AVAILABLE, broker-2: AVAILABLE), subscribers = 4, published events = 6, refused publications = 0, delivered = 20, undelivered = 3, queued = 0
```

Серверная строка:

```
[19:27:47.325] [Client] → [PUBLISHER] PUBLISHED PaymentCompleted #E6, brokers: broker-2 → 1 subscriber(s), refused: broker-1 (broker 'broker-1' is UNAVAILABLE: broker process stopped); subscribers process the event asynchronously
[19:27:47.325] [Client] → SUCCESS PaymentCompleted #E6 published to broker-2 → 1 subscriber(s); refused by broker-1 (broker 'broker-1' is UNAVAILABLE: broker process stopped)
```

Отказ Broker-а смоделирован изменением состояния (`FailBroker`), процесс сервера не убивался.
Это позволяет показать поведение Publisher-а и сохранение работы второго Broker-а без потери
управления экспериментом.

Дополнительные проблемы, которые появляются при нескольких Broker-ах:

| Проблема | Как проявляется | Что сделано в работе |
|---|---|---|
| Дублирование доставки | если один Subscriber зарегистрировать на двух Broker-ах, он получит событие дважды | в топологии каждый Subscriber закреплён за одним Broker-ом |
| Порядок событий | два Broker-а обрабатывают события параллельно, глобальный порядок не гарантирован | для журнала и статистики используется `EventId` и время события; жёсткий порядок не требуется |
| Потеря очереди при падении процесса | очередь хранится в памяти Broker-а | отказ смоделирован логически; ограничение отмечено в выводах |
| Сложность мониторинга | нужно смотреть состояние и очередь каждого Broker-а | команда `PubSubStatus` возвращает состояние обоих Broker-ов и всех подписчиков |
| Разная скорость подписчиков | один Broker может отставать от другого | у каждого Broker-а свои `Task.Run` и свой `WaitUntilIdle` |

### Требование 2. Очередь событий

Очередь реализована в `EventBroker`:

```
Publisher → Broker.Accept → Task.Run(DeliverOnce)
                              │
                              ├── SUCCESS → запись DeliveryRecord
                              └── ошибка → PendingDelivery в _pending
                                             │
                                             ▼
                                        RetryPending
                                             │
                                             ▼
                                        Subscriber
```

`PendingDelivery` хранит событие, подписчика, номер попытки и последнюю ошибку. В журнал
пишется явная строка `QUEUED`:

```
[19:27:09.892] [Client] → [QUEUE broker-1] QUEUED BookingCreated #E2 for RoomService - kept in the broker queue, 1 delivery(ies) waiting
[19:27:37.358] [Client] → [QUEUE broker-2] QUEUED BookingCreated #E1 for AnalyticsService - kept in the broker queue, 1 delivery(ies) waiting
[19:27:41.190] [Client] → [QUEUE broker-2] QUEUED PaymentCompleted #E2 for AnalyticsService - kept in the broker queue, 1 delivery(ies) waiting
```

Событие не теряется, если Subscriber недоступен:

| Событие | Когда попало в очередь | Когда доставлено | Итог |
|---|---|---|---|
| `BookingCreated #E2` для `RoomService` | 19:27:09.892 | 19:27:14.902 | `Attempt 2 → SUCCESS`, очередь 0 |
| `BookingCreated #E1` для `AnalyticsService` | 19:27:37.358 | 19:27:41.179 | `Attempt 2 → SUCCESS`, очередь 0 |
| `PaymentCompleted #E2` для `AnalyticsService` | 19:27:41.190 | 19:27:43.996 | `Attempt 3 → SUCCESS`, очередь 0 |

### Требование 3. Повторная доставка

Повторная доставка выполняется командой `RetryPending`. Номер попытки увеличивается, каждая
попытка пишется в журнал. Пример с двумя неудачными попытками и третьей успешной:

| Попытка | Результат | Строка журнала |
|---:|---|---|
| 1 | `FAIL` | `[AnalyticsService] FAIL PaymentCompleted #E2: subscriber 'AnalyticsService' failed to process the event: handler fails twice, then recovers` |
| 1 | в очередь | `[QUEUE broker-2] QUEUED PaymentCompleted #E2 for AnalyticsService - kept in the broker queue, 1 delivery(ies) waiting` |
| 2 | `FAIL` | `[RETRY broker-2] Attempt 2 → FAIL (subscriber 'AnalyticsService' failed to process the event: handler fails twice, then recovers), 1 attempt(s) left, the event stays in the queue` |
| 3 | `SUCCESS` | `[RETRY broker-2] Attempt 3 → SUCCESS - PaymentCompleted #E2 reached AnalyticsService, the event was not lost while the subscriber was down` |

Итог:

```
[19:27:43.997] [Client] → [RETRY -] RETRY DONE - 1 event(s) reached their subscribers, 0 remained undelivered, queue left = 0
[19:27:43.997] [Client] → SUCCESS Redelivery: 1 recovered, 0 not delivered this pass, queue = 0
```

После `MaxAttempts = 3` событие помечается потерянным для этого подписчика:

```
DROP PaymentCompleted #E2 for AnalyticsService - 3 attempt(s) failed, the event is lost for this subscriber
```

Это проверяет тест `EventBroker_RetryPending_WhenAttemptsAreExhausted_DropsEventAndEmptiesQueue`.
В эксперименте с тремя попытками событие было доставлено на третьей попытке, поэтому очередь
закончилась нулём.

### Требование 4. Новый тип Subscriber: AnalyticsService

`AnalyticsService` добавлен в Часть 5:

- подписан на все три типа событий;
- не обращается к базе данных;
- не меняет состояние `RoomService`;
- считает количество событий по типам и количество различных клиентов;
- возвращает строку `analytics: BookingCreated = 1, PaymentCompleted = 1, clients = 1`.

Строка статистики из `07-part5-brokers.log`:

```

```

Доказательство того, что подписчики не меняют данные предметной области, из
`11-domain-data-proof.log`:

Содержимое таблиц после событий:

что `AnalyticsService` подписан на все три типа и получал события, которые `RoomService` или
`NotificationService` не получали.

### Требование 6. Анализ задержек

Таблица из `07-part5-brokers.log`:

| Событие | Клиент | Время публикации, мс | Время доставки, мс | Время обработки, мс | Завершение всех Subscriber, мс |
|---|---|---|---:|---:|---:|---:|
| `BookingCreated #E1` | Client | 1 | 1003 | 3003 | 3822 |
| `PaymentCompleted #E2` | Client | 0 | 1000 | 2002 | 2807 |
| `BookingCreated #E3` | Client #2 | 0 | 801 | 3002 | 3002 |
| `BookingCreated #E4` | Client #3 | 0 | 800 | 3000 | 3000 |
| `BookingCreated #E5` | Client #1 | 0 | 800 | 2999 | 3000 |

Что показывают эти числа:

1. **Время публикации** - 0-1 мс. Publisher не ждёт подписчиков, он только передаёт событие
   Broker-ам и возвращает результат.
2. **Время доставки** - 800-1003 мс. Оно близко к задержке самого быстрого подписчика
   (`AnalyticsService` - 800 мс, `Logger` - 1000 мс), потому что фиксируется первая успешная
   доставка.
3. **Время обработки** - 2002-3003 мс. Оно определяется самым медленным подписчиком:
   `RoomService` - 3000 мс, `NotificationService` - 2000 мс.
4. **Завершение всех Subscriber** - 2805-3822 мс. В обычном случае это максимальная задержка
   (3000-3002 мс). У событий `#E1` и `#E2` значение больше, потому что в этом прогоне
   `AnalyticsService` был недоступен, событие ждало в очереди и после восстановления
   доставлялось повторно: 3822 мс у `#E1` и 2807 мс у `#E2` включают ожидание в очереди и
   повторную доставку, а не только обработку.

Таким образом, задержки подтверждают независимость подписчиков: одно и то же событие
обрабатывается разное время, но публикация и ответ сервера не зависят от самой медленной
обработки.

## 10. Контрольные вопросы

**1. Что такое Pub/Sub?**
Это модель взаимодействия, в которой Publisher публикует событие, а Subscriber-ы заранее
подписываются на интересующие их типы событий. Между ними находится Broker: он принимает
событие, хранит подписки, определяет получателей и доставляет им событие. Publisher не знает
состав подписчиков и не вызывает их напрямую.

**2. Что такое Publisher?**
Компонент, который принимает событие от сервера и передаёт его Broker-у. В работе это
`EventPublisher`: он хранит только список `EventBroker`, вызывает `Accept` и возвращает
`PublicationResult` с информацией о том, какие Broker-ы приняли событие, а какие отказали.

**3. Что такое Broker?**
Компонент, который принимает события, хранит подписки, определяет подписчиков, передаёт им
события, фиксирует ошибки доставки и продолжает работу при отказе отдельного Subscriber.
В работе это `EventBroker`; в проекте два Broker-а: `broker-1` и `broker-2`.

**4. Что такое Subscriber?**
Компонент, который подписывается на типы событий и обрабатывает их. В работе четыре
подписчика по умолчанию: `Logger`, `RoomService`, `NotificationService`, `AnalyticsService`.
`AuditService` и `ReportService` добавляются во время работы.

**5. Что такое Event?**
Сообщение о произошедшем факте. В работе `DomainEvent` содержит `EventId`, `EventType`,
`EntityId`, `Timestamp`, `ClientId` и `Data`. Например, `BookingCreated #E1` с
`EntityId = 1` и данными `room = 101, guest = 1, total = 200.00`.

**6. Как взаимодействуют Publisher и Broker?**
Publisher вызывает `broker.Accept(domainEvent, clientId)` для каждого Broker-а. Broker
проверяет своё состояние, определяет получателей через `RecipientsOf`, запускает доставку в
`Task.Run` и возвращает число подписчиков, которым событие отправлено. Если Broker недоступен,
Publisher получает отказ и продолжает работу с остальными Broker-ами.

**7. Может ли один Subscriber получать несколько типов событий?**
Да. `Logger` и `AnalyticsService` подписаны на все три типа, `NotificationService` - на
`BookingCreated` и `PaymentCompleted`. Это видно в таблице подписок раздела 2 и в журнале
`Subscribe(BookingCreated, BookingCancelled, PaymentCompleted)`.

**8. Что такое слабая связанность компонентов?**
Это ситуация, когда компоненты знают друг о друге минимум. Publisher знает только Broker,
Broker знает подписки, Subscriber знает свой Broker и типы событий. Сервер не содержит списка
подписчиков и не вызывает их напрямую. Благодаря этому `AuditService` и `ReportService` были
добавлены без изменения Publisher-а и бизнес-операций.

**9. Почему Publisher не должен напрямую обращаться к Subscriber?**
Потому что тогда Publisher начнёт знать состав подписчиков, их расположение и способ
обработки. При добавлении нового компонента пришлось бы менять Publisher. В Pub/Sub Publisher
передаёт событие Broker-у, а Broker сам находит получателей. Это уменьшает связанность и
позволяет добавлять подписчиков без пересборки публикующего кода.

**10. Для чего используется асинхронная обработка событий?**
Чтобы публикация и ответ сервера не зависели от времени обработки подписчиков. В работе
публикация занимает 0-1 мс, а `RoomService` обрабатывает событие 3000 мс. Сервер отвечает
клиенту сразу, а подписчики работают в отдельных задачах. Это также позволяет одному
медленному подписчику не блокировать остальных.

**11. Как проверить, что Subscriber не получает событие, на которое он не подписан?**
Нужно сравнить списки получателей для каждого типа. В `03-part2-subscribers.log`:
`PaymentCompleted #E2: получили = Logger, NotificationService, AnalyticsService, не получили = RoomService`;
`BookingCancelled #E3: получили = Logger, AnalyticsService, не получили = NotificationService, RoomService`.
Дополнительно это проверяют тесты `EventBroker_Accept_SkipsSubscriberWithoutSubscriptionOnThatType`
и `EventBroker_Accept_KeepsEventWhenNobodySubscribedToItsType`.

**12. Что произойдёт при отсутствии подписчиков на событие?**
Broker примет событие и запишет его в свой журнал, но `RecipientsOf` вернёт пустой список,
поэтому доставок не будет. В журнал будет добавлена строка
`no subscribers for <EventType> - event received but nobody will process it`. Publisher
получит результат с нулевым числом подписчиков. Сервер не падает: отсутствие подписчиков -
это не ошибка, а отсутствие заинтересованных компонентов.

**13. Что произойдёт, если Broker недоступен?**
Publisher вызывает `Accept`, получает `BrokerUnavailableException` и записывает отказ в
`RefusedBy`. Если жив хотя бы один Broker, событие публикуется через него; если недоступны
все, `PublicationResult.IsSuccess = false`, а сервер продолжает работу. В `07-part5-brokers.log`
при отказе `broker-1` событие `PaymentCompleted #E6` было опубликовано через `broker-2`.

**14. Какие преимущества даёт Pub/Sub при добавлении новых компонентов?**
Не нужно менять Publisher и бизнес-операции. Достаточно зарегистрировать подписчика и указать
подписки. В работе `AuditService` был добавлен во время работы сервера, получил
`BookingCreated` и обработал его, а `Publisher` остался тем же: в нём только список Broker-ов.
`ReportService` аналогично получил `BookingCancelled` без изменения публикующего кода.

**15. Какие недостатки может иметь Pub/Sub?**
Событие обрабатывается не сразу, а асинхронно, поэтому клиент не получает результат обработки
в ответе на операцию. Появляются вопросы доставки: очередь, повторные попытки, возможные
дубликаты и порядок событий. Нужны мониторинг Broker-ов, журналирование и обработка отказов.
Сам Broker становится важным компонентом: при его недоступности часть подписчиков не получает
события. В учебной реализации очередь хранится в памяти, поэтому при падении процесса она
теряется.

**16. Какие проблемы могут возникнуть при большом количестве событий?**
Очередь может расти быстрее, чем подписчики успевают обрабатывать события; увеличиваются
задержка доставки, память и нагрузка на Broker. Нужны ограничение очереди, backpressure,
пакетная обработка, несколько Broker-ов или партиционирование, сохранение очереди на диск и
мониторинг. В текущей работе очередь `_pending` не ограничена, а принятые события хранятся
в памяти; для учебного эксперимента этого достаточно, для промышленной системы потребовался
бы внешний брокер или собственная персистентная очередь.

## 13. Выводы

1. Модель Pub/Sub реализована средствами C# без Kafka, RabbitMQ и ActiveMQ: есть `Event`,
   `EventPublisher`, `EventBroker`, `ISubscriber`, журнал публикации и доставки.
2. Базовая доставка работает: одно событие `BookingCreated #E1` получили четыре подписчика
   через два Broker-а. Публикация заняла 1 мс, а самая долгая обработка - 3004 мс, то есть
   сервер ответил клиенту, не дожидаясь подписчиков.
3. В работе три типа событий: `BookingCreated`, `PaymentCompleted`, `BookingCancelled`.
   `Logger` и `AnalyticsService` получают все три, `NotificationService` - два,
   `RoomService` - только `BookingCreated`. Фильтрация подтверждена таблицей «получили / не
   получили» и тестами.
4. Асинхронная обработка и искусственные задержки работают независимо: `Logger` - 1000 мс,
   `NotificationService` - 2000 мс, `RoomService` - 3000 мс, `AnalyticsService` - 800 мс.
5. Отказ `RoomService` не остановил остальных: три подписчика получили `SUCCESS`, один -
   `UNAVAILABLE`, событие осталось в очереди. После восстановления повторная доставка
   `Attempt 2 → SUCCESS` вернула очередь к нулю. Сервер остался жив.
6. Проверены три способа отказа подписчика: остановка, ошибка соединения и искусственное
   исключение. Все они различаются в журнале (`UNAVAILABLE`, `CONNECTION ERROR`,
   `PROCESSING ERROR`) и не приводят к падению сервера.
7. Новый `AuditService` добавлен во время работы без изменения Publisher-а: подписчиков стало
   5, событие `BookingCreated` получили все пять, `AuditService` записал
   `audit entry: BookingCreated of booking 3 ...`. `ReportService` аналогично получил
   `BookingCancelled` в полном цикле.
8. Полный цикл Части 4 воспроизведён в одном прогоне: операция → событие → публикация →
   приём → определение подписчиков → доставка нескольким → отказ одного → работа остальных →
   новый подписчик → получение события новым подписчиком.
9. Два Broker-а работают: при отказе `broker-1` событие `PaymentCompleted #E6` опубликовано
   через `broker-2`; после восстановления `broker-1` снова принимает события. Очередь
   `PendingDelivery` сохраняет событие, пока подписчик недоступен.
10. Повторная доставка реализована по схеме `Attempt 1 → FAIL`, `Attempt 2 → FAIL`,
    `Attempt 3 → SUCCESS`. После исчерпания `MaxAttempts = 3` событие помечается потерянным
    для конкретного подписчика.
11. `AnalyticsService` собирает статистику и не меняет данные предметной области: отпечатки
    `bookings`, `payments` и `rooms` до и после событий совпадают (`26a00a316b2dbfe34505c128f635205b`
    для `rooms`, `bookings` и `payments` пусты). Это же подтверждает тест
    `DbBookingService_EventSubscribers_LeaveDomainDataUntouched`.
12. Несколько клиентов работают одновременно: `Client A` и `Client B` публикуют свои события
    под своими идентификаторами, а `AnalyticsService` учитывает обоих (`clients = 2`).
13. Все 13 ситуаций ошибок обработаны как ожидаемые результаты, а не как аварийное завершение.
    При недоступном Broker-е Publisher получает понятный отказ, при недоступном Subscriber-е
    остальные продолжают работу.
14. Механизм закреплён 46 unit-тестами; общий прогон - 165 тестов, все зелёные. Регрессия
    ЛР №4 и ЛР №5 (119 тестов) сохранена.
15. Итоговый прогон `09-final-cycle.log`: `published events = 17`, `refused publications = 0`,
    `delivered = 67`, `undelivered = 7`, `queued = 0`. Семь записей `undelivered` - это
    неудачные попытки доставки, которые были повторены; после повторной доставки очередь пуста.

### Ограничения учебной реализации

1. Broker и очередь живут в памяти процесса. При реальном падении процесса очередь
   `PendingDelivery` теряется; в экспериментах отказ Broker-а и подписчика моделируется
   изменением состояния, а не убийством процесса.
2. Каждый Subscriber закреплён за одним Broker-ом. Это исключает дублирование доставки, но
   не даёт автоматического перераспределения подписчиков между Broker-ами.
3. Очередь `_pending` не ограничена по размеру, а список принятых событий `_received`
   ограничен 50 записями. При большом потоке событий нужны backpressure, персистентность и
   мониторинг.
4. Гарантия доставки - «не менее одного раза» в рамках работы процесса: при повторной
   доставке подписчик может получить событие повторно, если успел обработать его, но ответ
   не был зафиксирован. Для промышленной системы нужна идемпотентность обработчиков.
5. Глобальный порядок событий между Broker-ами не гарантируется. В работе это не мешает,
   потому что события содержат `EventId` и время, а подписчики не требуют строгой
   последовательности.
