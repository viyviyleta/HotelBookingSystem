## 2. Теоретические сведения

### 2.1. CI/CD

**CI/CD** — совокупность практик автоматизации разработки, проверки, сборки и доставки ПО.

- **Continuous Integration (CI)** — регулярное объединение изменений исходного кода с общей
  версией проекта и автоматическая проверка результата: получение кода, восстановление
  зависимостей, сборка, тесты.
- **Continuous Delivery (CD)** — автоматическая подготовка проверенной версии к развёртыванию:
  после успешных проверок создаётся готовый артефакт (Docker-образ), но само развёртывание
  может требовать ручного подтверждения.
- **Continuous Deployment** — успешно прошедшие проверки изменения автоматически
  развёртываются в целевой среде без ручного подтверждения.

В ЛР реализован вариант, соответствующий **Continuous Deployment**: после успешной сборки,
тестов и создания образа Pipeline сам обновляет Deployment в Kubernetes.

### 2.2. Pipeline и его этапы

**Pipeline** — последовательность автоматизированных этапов обработки изменений кода.

| Этап | Назначение | Команда/действие |
|---|---|---|
| Checkout | получение исходного кода из Git | `checkout scm` |
| Restore | восстановление зависимостей .NET | `dotnet restore` |
| Build | сборка проекта | `dotnet build -c Release` |
| Test | запуск Unit-, интеграционных и нагрузочных тестов | `dotnet test` |
| Package | создание Docker-образа | `docker build` |
| Deploy | развёртывание новой версии в Kubernetes | `kubectl set image` |

Переход к следующему этапу возможен только после успешного выполнения предыдущего.
Если Unit-тесты завершились ошибкой, Pipeline получает статус **Failed**, а Package и Deploy
не выполняются. Именно это свойство и проверялось в экспериментах.

### 2.3. Jenkins

**Jenkins** — сервер автоматизации, который выполняет задания (Job) по заданным правилам:
получает код из Git, запускает команды сборки, тестов, Docker и kubectl, сохраняет журналы и
отображает результат.

**Jenkins Job** — отдельное задание. **Jenkins Pipeline** — описание последовательности этапов.
В ЛР используется хранение Pipeline в файле `Jenkinsfile` внутри Git-репозитория (второй способ,
требуемый заданием), а не описание непосредственно в интерфейсе.

### 3.4. Настройка Jenkins Job

Для реального Jenkins используется следующая последовательность:

1. Открыть веб-интерфейс Jenkins.
2. Создать новый Job с типом **Pipeline**, имя — `RIOT-CICD`.
3. В разделе Pipeline выбрать **Pipeline script from SCM**.
4. SCM — **Git**, указать URL локального или удалённого репозитория.
5. Указать ветку `master` (или `*/master`).
6. Указать путь к файлу сценария: `Jenkinsfile` (в корне репозитория).
7. При необходимости включить **Poll SCM** с расписанием `H/2 * * * *` или настроить Webhook.
8. Сохранить Job и выполнить **Build Now**.

Если репозиторий закрытый, предварительно добавляются учётные данные Jenkins
(*Manage Jenkins → Credentials*) и выбираются в настройках SCM. Пароли и токены не размещаются
в `Jenkinsfile` и в открытом репозитории.

### 3.5. Jenkinsfile и этап Checkout

В корне репозитория создан `Jenkinsfile`:

```groovy
pipeline {
    agent any

    options {
        disableConcurrentBuilds()
        buildDiscarder(logRotator(numToKeepStr: '10'))
    }

    environment {
        SOLUTION       = 'HotelBookingSystem.slnx'
        SERVER_PROJECT = 'Server/Server.csproj'
        TESTS_PROJECT  = 'Tests/Tests.csproj'
        IMAGE_NAME     = 'riot-server'
        IMAGE_TAG      = "${env.BUILD_NUMBER}"
        DOCKERFILE     = 'Server/Dockerfile'
        DEPLOYMENT     = 'riot-server'
        CONTAINER      = 'server'
        NAMESPACE      = 'default'
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
                sh '''
                    echo "=== Checkout ==="
                    git rev-parse --abbrev-ref HEAD
                    git rev-parse HEAD
                    git log -1 --oneline
                '''
            }
        }
        // остальные этапы приведены ниже
    }
}
```

`checkout scm` получает исходный код из репозитория, указанного в настройках Job. Команды
`git rev-parse` и `git log` позволяют увидеть, какая ветка и какой commit попали в сборку.
Для Jenkins под Windows команды `sh` заменяются на `bat`; в данной работе среда macOS/Linux,
поэтому используется `sh`.

### 4.5. Итоговый Jenkinsfile для CI

После добавления этапов Checkout, Restore, Build и Test последовательность имеет вид:

```groovy
pipeline {
    agent any
    stages {
        stage('Checkout') { steps { checkout scm } }
        stage('Restore')  { steps { sh 'dotnet restore HotelBookingSystem.slnx' } }
        stage('Build')    { steps { sh 'dotnet build HotelBookingSystem.slnx -c Release --no-restore' } }
        stage('Test')     { steps { sh 'dotnet test Tests/Tests.csproj -c Release --no-build' } }
    }
}
```

### 4.6. Проверка получения актуального кода

Для проверки было внесено корректное изменение в серверный код — в
`Server/ServerListener.cs` добавлена строка:

```csharp
ServerLog.Info("SERVER", "LR10 build marker: pipeline-v2");
```

Изменение зафиксировано коммитом `3369de2` и повторно прогнано через Pipeline. Checkout показал
новый commit, сборка и тесты прошли, а после Deploy в журнале нового Pod появилась строка
`LR10 build marker: pipeline-v2`. Это доказывает, что Jenkins/исполнитель получает именно
актуальную версию кода, а не повторно запускает старый образ.

Для периодической проверки репозитория в настройках Job можно включить **Poll SCM**:

```
H/2 * * * *
```

Это означает проверку примерно раз в две минуты; фактическое время определяет планировщик
Jenkins. Альтернатива — GitHub Webhook, который уведомляет Jenkins сразу после `push`.

### 6.4. Этап Deploy

```groovy
stage('Deploy') {
    steps {
        sh '''
            kubectl config current-context
            kubectl config set-context --current --namespace="${NAMESPACE}"

            kubectl set image "deployment/${DEPLOYMENT}" \
                "${CONTAINER}=${IMAGE_NAME}:${IMAGE_TAG}" \
                --namespace="${NAMESPACE}"

            kubectl rollout status "deployment/${DEPLOYMENT}" \
                --namespace="${NAMESPACE}" \
                --timeout=180s

            kubectl get deployment "${DEPLOYMENT}" --namespace="${NAMESPACE}"
            kubectl get pods -l app="${DEPLOYMENT}" --namespace="${NAMESPACE}" -o wide
        '''
    }
}
```

`kubectl set image deployment/riot-server server=riot-server:14` обновляет образ контейнера

- содержит исходный код проекта;
- содержит исходный код тестов;
- содержит `Server/Dockerfile`;
- содержит `Jenkinsfile`;
- содержит конфигурационные файлы и манифесты `k8s/`;
- не содержит открытых паролей, токенов и других секретных данных (`.env` и `k8s/secret.yaml`
  исключены через `.gitignore`).

### Jenkins Pipeline

- получает исходный код из Git (`checkout scm`);
- восстанавливает зависимости (`dotnet restore`);
- собирает проект (`dotnet build -c Release`);
- запускает тесты (`dotnet test`);
- создаёт Docker-образ после успешных проверок (`docker build`);
- использует уникальный тег (`BUILD_NUMBER`);
- выполняет развёртывание в Kubernetes (`kubectl set image`);
- проверяет результат обновления (`kubectl rollout status`);
- прекращает выполнение последующих этапов при ошибке обязательного этапа;
- отображает результат выполнения и сообщения об ошибках (Console Output, статус Success/Failed).

### Конфигурация Kubernetes

- содержит Deployment `riot-server`;
- использует правильный Docker-образ;
- содержит Service `riot-server` (ClusterIP, порт `5377`);
- позволяет проверить состояние Pod;
- позволяет обновлять используемый Docker-образ;
- обеспечивает доступность приложения после успешного развёртывания.

## 10. Ответы на контрольные вопросы

**1. Что такое Continuous Integration?**
Практика регулярного объединения изменений исходного кода с общей версией проекта и
автоматической проверки результата: получение кода, восстановление зависимостей, сборка,
тесты. Цель — рано обнаруживать ошибки и не допускать их накопления.

**2. Что такое Continuous Delivery?**
Практика автоматической подготовки проверенной версии приложения к развёртыванию. После
успешной сборки и тестирования создаётся готовый артефакт (например, Docker-образ), который
можно развернуть; само развёртывание может требовать ручного подтверждения.

**3. Чем Continuous Delivery отличается от Continuous Deployment?**
В Continuous Delivery развёртывание в целевую среду запускается после дополнительного
подтверждения, а в Continuous Deployment успешно прошедшие проверки изменения развёртываются
автоматически, без ручного подтверждения.

**4. Что такое Pipeline?**
Последовательность автоматизированных этапов обработки изменений кода. Каждый этап отвечает
за определённую операцию: получение кода, восстановление зависимостей, сборку, тесты,
создание образа, развёртывание.

**5. Для чего используется Jenkins?**
Для автоматизации сборки, тестирования и доставки ПО. Jenkins получает код из Git, запускает
команды, выполняет тесты, создаёт образы, взаимодействует с Kubernetes, сохраняет журналы и
отображает результат.

**6. Что такое Jenkins Job?**
Отдельное задание Jenkins, которое выполняется по заданным правилам: вручную, по расписанию
или по событию (Webhook). Job содержит настройки репозитория, триггеры и описание Pipeline.

**7. Чем Jenkins Pipeline отличается от обычного Jenkins Job?**
Обычный Job описывает отдельные шаги (например, команды сборки) в интерфейсе. Pipeline
описывает последовательность этапов, может храниться в `Jenkinsfile` вместе с кодом,
версионироваться и поддерживать сложные сценарии (условия, параллельные ветки, обработку
ошибок, сохранение артефактов).

**8. Что такое Jenkinsfile?**
Текстовый файл с описанием Pipeline, который хранится в Git-репозитории рядом с исходным
кодом. Он позволяет версионировать процесс автоматизации и использовать один и тот же
сценарий для разных сборок.

**9. Для чего используется этап Restore?**
Для восстановления зависимостей проекта (`dotnet restore`): получения необходимых пакетов и
подготовки проекта к сборке. Это также проверяет, что зависимости доступны и корректны.

**10. Почему тесты необходимо запускать до создания Docker-образа?**
Чтобы не создавать и не доставлять образ с некорректной логикой. Если тесты не проходят,
дальнейшие этапы останавливаются, и в целевую среду не попадает версия, не прошедшая проверки.

**11. Что происходит, если тесты завершаются ошибкой?**
`dotnet test` возвращает ненулевой код, Jenkins помечает этап и весь Pipeline как Failed и
прекращает выполнение последующих этапов (если для них не настроено специальное поведение).
Package и Deploy не выполняются.

**12. Что выполняется на этапе Package?**
Создание Docker-образа приложения командой `docker build`, присвоение имени и тега (в ЛР —
номер сборки Jenkins), проверка информации об образе через `docker image inspect`.

**13. Для чего используется этап Deploy?**
Для обновления работающего приложения в Kubernetes: `kubectl set image` меняет образ
контейнера в Deployment, `kubectl rollout status` ожидает завершения обновления, после чего
проверяются Deployment, Pod и доступность приложения.

**14. Как Jenkins может обновить Docker-образ в Kubernetes Deployment?**
Например, командой `kubectl set image deployment/riot-server server=riot-server:<tag>`.
Kubernetes создаёт новые Pod с указанным образом и постепенно заменяет старые.

**15. Для чего используется команда `kubectl rollout status`?**
Чтобы дождаться завершения обновления Deployment и получить информацию о результате.
Если обновление не завершилось (например, новый Pod не готов), команда завершится ошибкой,
и Pipeline сможет пометить этап Deploy как неуспешный.

**16. Почему Jenkins должен иметь доступ к Kubernetes?**
Потому что этап Deploy выполняет команды `kubectl`, которым нужен доступ к кластеру:
корректный kubeconfig/контекст и права на изменение Deployment и чтение Pod. Без этого
развёртывание невозможно.

**17. Что такое Poll SCM?**
Механизм периодической проверки Git-репозитория на наличие новых изменений. Если Jenkins
обнаруживает новый commit, он запускает задание. Расписание задаётся в формате cron,
например `H/2 * * * *`.

**18. Что может привести к неуспешному выполнению Jenkins Pipeline?**
Ошибки компиляции, неуспешные тесты, недоступность Git-репозитория или неверные учётные
данные, недоступность Docker или Kubernetes, неверное имя Deployment/контейнера,
отсутствующий Docker-образ или тег, неверный kubeconfig/контекст, ошибки в `Jenkinsfile`,
недоступность зависимых сервисов (например, базы данных).

## 11. Выводы

В работе создан CI/CD Pipeline для клиент-серверного приложения бронирования отелей.
Pipeline описан в `Jenkinsfile` и включает этапы Checkout, Restore, Build, Test, Package
и Deploy. Проверено, что:

- Jenkins/исполнитель получает актуальный исходный код из Git;
- зависимости восстанавливаются, проект собирается в конфигурации Release;
- автоматически выполняются 253 теста, результаты сохраняются в TRX;
- при ошибке тестирования Pipeline останавливается, Package и Deploy не выполняются;
- Docker-образ создаётся только после успешных проверок и получает уникальный тег;
- образ автоматически разворачивается в Kubernetes, Deployment обновляется, Pod переходят
  в состояние `Running`;
- при ошибке Deploy Pipeline получает статус Failed, а прежняя версия остаётся доступной;
- контрольные операции предметной области выполняются через Service, новая версия
  подтверждается маркером в журнале Pod.

Автоматизация сокращает ручные операции, уменьшает риск доставки непроверенной версии и
позволяет быстро и воспроизводимо обновлять приложение. Ограничения учебной конфигурации:
локальный Jenkins/исполнитель, локальный Kubernetes с одним узлом, общий Docker Engine,
`emptyDir` для PostgreSQL и отсутствие внешнего registry — для производственной среды
потребовались бы удалённый registry, постоянное хранилище, резервное копирование и
разграничение прав.

# Проверка инструментов
dotnet --version
git --version
docker --version
kubectl version --client

# Локальный прогон Pipeline (эквивалент Jenkinsfile)
BUILD_NUMBER=14 VERIFY=1 ./scripts/run_lr10_pipeline.sh

docker image inspect riot-server:14
