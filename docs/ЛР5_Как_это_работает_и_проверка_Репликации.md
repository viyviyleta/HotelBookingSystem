# ЛР №5. Как устроена репликация и как проверить её самостоятельно

Разбор по варианту 2 (бронирование отелей, ресурс - `rooms.is_available`).
Документ отвечает на три вопроса: где в коде Primary и Replica, как изменение попадает
из одной копии в другую, и как убедиться, что копия действительно обновилась, не веря
приложению на слово.

---

## 1. Две копии = две схемы в одной базе

```
PostgreSQL localhost:5432, база hotelbooking
│
├── схема riot_primary    ← Primary
│     hotels, rooms, guests, bookings, payments   (PK, FK, CHECK, sequence - свои)
│
└── схема riot_replica    ← Replica
      hotels, rooms, guests, bookings, payments   (идентичная структура, свои данные)
```

Сервер подключается к одной базе, но каждой копии даёт свою схему: строка подключения
содержит `search_path`, а все запросы к таблицам копии квалифицируются именем схемы
(`DatabaseInstance.Qualify("rooms")` → `riot_replica.rooms`). Копии не делят таблицы, поэтому
запись в Primary физически не может попасть в Replica помимо механизма репликации, и
наоборот. Сервер сам создаёт недостающую схему (`HotelDatabase.EnsureSchema`), поэтому для
 Replica не нужно ни `createdb`, ни ручной DDL.

Имя схемы попадает в SQL только после проверки `HotelDatabase.IsSafeIdentifier`
(шаблон `^[a-z][a-z0-9_]*$`) - это единственный случай, когда идентификатор подставляется
в текст запроса; все значения клиентов передаются параметрами.

## 3. Как изменение попадает в Replica

Последовательная репликация (методичка разрешает): изменение сначала подтверждено в
serving-копии, затем копируется.

1. Клиент присылает `CreateBooking` / `PayBooking` / `CancelBooking`.
2. `InstanceCluster.Route` проверяет состояние экземпляров и возвращает Primary
   (или Replica, если Primary недоступен).
3. `BookingStore` выполняет операцию в своей схеме, при `--tx on` - в транзакции COMMIT.
4. `Replicator.ReplicateChange(source, target, ids)` переносит затронутые строки:

```sql
-- брони: идемпотентно, повтор не создаёт дублей (Replicator.CopyBookings)
INSERT INTO riot_replica.bookings (id, room_id, guest_id, check_in_date, check_out_date, total_amount, status)
SELECT id, room_id, guest_id, check_in_date, check_out_date, total_amount, status
  FROM riot_primary.bookings WHERE id = ANY(@ids)
ON CONFLICT (id) DO UPDATE
   SET room_id = EXCLUDED.room_id, guest_id = EXCLUDED.guest_id,
       check_in_date = EXCLUDED.check_in_date, check_out_date = EXCLUDED.check_out_date,
       total_amount = EXCLUDED.total_amount, status = EXCLUDED.status;

-- платежи: тот же паттерн, только отбор по booking_id = ANY(@ids)  (CopyPayments)

-- состояние номера (главный ресурс варианта 2): затронутые номера и номера из перенесённых броней
UPDATE riot_replica.rooms t SET is_available = s.is_available
  FROM riot_primary.rooms s
 WHERE s.id = t.id
   AND (t.id = ANY(@rooms) OR s.id IN (SELECT room_id FROM riot_primary.bookings WHERE id = ANY(@bookings)));

-- полная синхронизация (Synchronize) идёт в одной транзакции: очистка приёмника, перенос всех
-- строк bookings/payments, перенос is_available по всем rooms, затем выравнивание счётчиков:
SELECT setval(pg_get_serial_sequence('riot_replica.bookings','id'),
              (SELECT COALESCE(MAX(id), 0) + 1 FROM riot_replica.bookings), false);
```

`@ids`, `@bookings`, `@rooms` - параметры, значения в текст SQL не подставляются. Порядок
журнала одной операции: `[REPLICATION] START …changed rows`, `[REPLICATION] UPDATE Replica
(schema '…')`, `[REPLICATION] SUCCESS — …: 1 booking row(s), 0 payment row(s), 1 room row(s)
copied`, `[RESULT] REPLICATION Primary → Replica: OK (rows: …)`.

5. Ответ клиенту содержит `ServedBy` (какая копия обслуживала) и `Replication` (чем
   закончилась передача), а `EventTriggered` - имя события: `PayBookingCommitted`,
   `ReplicationFailed`, `FailoverImpossible`, `ReplicasDiverged`, `SynchronizationDone`.

Отказ операции (номер уже занят, номер 999 не существует) репликации не вызывает: копировать
нечего, копии остаются равными.

## 4. Состояние копии и Failover

Состояние - это не только флаг в памяти. Перед каждым обращением к копии сервер делает
настоящий запрос `SELECT COUNT(*) FROM rooms` в её схеме:

| Ситуация | Что происходит | Метка в журнале |
|---|---|---|
| Штатная | Route выбирает Primary | `[ROUTING] request is redirected to Primary (…) — normal operation` |
| Отказ программно помечен | `FailInstance` меняет `State`, следующий запрос уходит в Replica | `[FAILURE] Primary → UNAVAILABLE (… reason = failure injected by Client at …)` |
| Копия реально недоступна | `Probe()` ловит ошибку соединения, копия помечается `UNAVAILABLE` | `[INSTANCE CHECK] Primary → UNAVAILABLE (… NOT CONNECTED — … 3D000 …)` |
| Primary недоступен | `Failover → START`, проверка Replica, запрос в неё | `[FAILOVER] SUCCESS — request redirected to Replica` |
| Обе недоступны | Переключать некуда, клиент получает текст с обеими причинами | `[FAILOVER] IMPOSSIBLE`, `EventTriggered = FailoverImpossible` |

Важная деталь: ошибка репликации не отменяет уже принятое изменение. Если в период отказа
изменение выполнено в Replica, а Secondary-копия (Primary) недоступна, клиент получает
`SUCCESS` плюс `EventTriggered = ReplicationFailed`, а расхождение фиксируется сверкой.

## 5. Recovery и синхронизация

`RestoreInstance(primary)` снова проверяет соединение и возвращает экземпляру
`AVAILABLE`; процесс сервера не перезапускается, и следующий запрос `Route` опять отдаёт
Primary (failback). После этого обязательно сравниваются копии: актуальной оказывается та,
где выполнялись изменения периода отказа (обычно Replica), и синхронизация запускается
в направлении `from=replica to=primary`:

```bash
# направление задаёт клиент (сценарии recovery / repl-cycle), либо SQL вручную
SynchronizeReplicas from=replica to=primary
```

Синхронизация отказывается работать, если источник и приёмник совпадают, источник
недоступен, роль указана неверно или источник физически недоступен - в каждом случае
возвращается текст, а не исключение.

## 6. Запуск

```bash
# один раз: база должна существовать; схемы сервер создаёт сам
createdb hotelbooking

# сервер с кластером (порт должен быть свободен)
dotnet run --project Server -- \
    --storage postgres --replication on --port 5356 --reserve-delay 300 \
    --primary-schema riot_primary --replica-schema riot_replica

# клиенты: по очереди или параллельно
dotnet run --project Client -- --port 5356 --name "Client 1" --scenario repl-status
dotnet run --project Client -- --port 5356 --name "Client 1" --scenario repl
dotnet run --project Client -- --port 5356 --name "Client 2" --scenario failover
dotnet run --project Client -- --port 5356 --name "Client 1" --scenario recovery
dotnet run --project Client -- --port 5356 --name "Client 1" --scenario repl-cycle
dotnet run --project Client -- --port 5356 --name "Client 1" --scenario repl-errors

# все эксперименты разом, логи в docs/logs/lr5/ (на ноутбуке - caffeinate, чтобы macOS не уснул)
PORT=5356 caffeinate -i ./scripts/run_lr5_experiments.sh

# тесты (119: 82 из ЛР №4 + 37 по ЛР №5)
dotnet test
```

Аргументы сервера по ЛР №5: `--replication on|off`, `--primary-schema`, `--replica-schema`,
`--primary-conn "<строка>"`, `--replica-conn "<строка>"`. При `--replication off` сервер
работает ровно как в ЛР №4, а операции ЛР №5 отвечают
`… is available only when the server is started with --replication on`.
Пароль в строках подключения не указывается: `libpq` берёт его из `PGPASSWORD` или `~/.pgpass`,
а в логи печатается только `host:port/database (schema …)`.

## 7. Проверка репликации без доверия к приложению

Все запросы ниже - средство СУБД; они и лежат в основе дампов `psql` после каждого
эксперимента в `docs/logs/lr5/`.

```sql
-- 1. обе копии живут в одной базе и видны как отдельные схемы
\dn
SELECT table_schema, table_name FROM information_schema.tables
 WHERE table_schema IN ('riot_primary','riot_replica') ORDER BY 1, 2;

-- 2. начальное совпадение: счётчики по главным таблицам
SELECT (SELECT COUNT(*) FROM riot_primary.rooms)               AS p_rooms,
       (SELECT COUNT(*) FROM riot_replica.rooms)               AS r_rooms,
       (SELECT COUNT(*) FROM riot_primary.bookings)            AS p_book,
       (SELECT COUNT(*) FROM riot_replica.bookings)            AS r_book,
       (SELECT COUNT(*) FROM riot_primary.payments)            AS p_pay,
       (SELECT COUNT(*) FROM riot_replica.payments)            AS r_pay;

-- 3. главный ресурс варианта 2: состояние каждого номера в двух копиях
SELECT COALESCE(p.id, r.id) AS room_id,
       p.is_available        AS in_primary,
       r.is_available        AS in_replica,
       p.is_available IS NOT DISTINCT FROM r.is_available AS match
      FROM riot_primary.rooms p FULL JOIN riot_replica.rooms r ON r.id = p.id
     ORDER BY 1;

-- 4. одна таблица-сводка: где именно копии разошлись (та же форма, что в логах)
SELECT 'rooms busy'      AS item,
       (SELECT COUNT(*) FROM riot_primary.rooms WHERE NOT is_available)  AS primary_,
       (SELECT COUNT(*) FROM riot_replica.rooms WHERE NOT is_available)  AS replica_
 UNION ALL SELECT 'bookings',
       (SELECT COUNT(*) FROM riot_primary.bookings), (SELECT COUNT(*) FROM riot_replica.bookings)
 UNION ALL SELECT 'bookings active',
       (SELECT COUNT(*) FROM riot_primary.bookings WHERE status <> 'Cancelled'),
       (SELECT COUNT(*) FROM riot_replica.bookings WHERE status <> 'Cancelled')
 UNION ALL SELECT 'payments',
       (SELECT COUNT(*) FROM riot_primary.payments), (SELECT COUNT(*) FROM riot_replica.payments);

-- 5. отпечаток строк: совпадение по content, а не только по количеству
SELECT (SELECT string_agg(id || '/' || room_id || '/' || guest_id || '/' || total_amount || '/' || status,
                          ',' ORDER BY id) FROM riot_primary.bookings) AS primary_fp,
       (SELECT string_agg(id || '/' || room_id || '/' || guest_id || '/' || total_amount || '/' || status,
                          ',' ORDER BY id) FROM riot_replica.bookings) AS replica_fp;

-- 6. sequence выровнены (признак того, что полная синхронизация прошла корректно;
--    у bookings/payments в обеих схемах свои identity-счётчики)
SELECT schemaname, sequencename, last_value FROM pg_sequences
 WHERE schemaname IN ('riot_primary','riot_replica') ORDER BY 1, 2;
```

Приложение и `psql` должны показывать одно и то же: после каждого успешного изменения в
Part 2 - `match = t` по всем строкам, после отказа Primary в Part 3 - `match = f` в
`rooms busy`, `bookings`, `bookings active`, после синхронизации в Part 4 - снова `t`.

## 8. Как проверить, что отказ настоящий, а не "сказанный"

Копии даётся строка подключения к несуществующей базе - приложение обязано обнаружить это
само, проверкой соединения, и продолжить работу через живую копию:

```bash
# Replica физически недоступна: Primary работает, сверка честно невозможна
dotnet run --project Server -- --storage postgres --replication on --port 5356 \
    --replica-conn "Host=localhost;Port=5432;Database=hotelbooking-missing;Username=$USER"
dotnet run --project Client -- --port 5356 --scenario repl-status      # лог 07-replica-down.log

# Primary физически недоступен: все запросы уходят в Replica
dotnet run --project Server -- --storage postgres --replication on --port 5356 \
    --primary-conn "Host=localhost;Port=5432;Database=hotelbooking-missing;Username=$USER"
dotnet run --project Client -- --port 5356 --scenario failover         # лог 08-primary-down.log
```

В ответе сервера появляется ошибка СУБД, а не выдуманная причина:

```
Replica = UNAVAILABLE (schema riot_replica, NOT CONNECTED — cannot open PostgreSQL database
'localhost:5432/hotelbooking-missing (schema riot_replica)':
3D000: database "hotelbooking-missing" does not exist)
```

Восстановление такой копии не требует `createdb`: достаточно `RestoreInstance` с корректной
строкой подключения, либо перезапуска с правильным `--replica-conn`.

## 9. Типичные препятствия на стенде

| Симптом | Причина | Что делать |
|---|---|---|
| `SocketException (48) address already in use` | порт занят предыдущим прогоном | `lsof -nP -iTCP:5356 -sTCP:LISTEN`, затем `PORT=5370 ./scripts/run_lr5_experiments.sh` |
| `53300: sorry, too many clients already` | каждая тестовая схема даёт свой пул соединений | в фикстуре вызывается `NpgsqlConnection.ClearAllPools()`; при ручном прогоне - закрыть лишние серверы |
| `3D000: database "hotelbooking" does not exist` | база не создана | `createdb hotelbooking` (схемы сервер создаёт сам) |
| `42P01: relation "riot_replica.rooms" does not exist` | копия реально недоступна - это ожидаемый результат эксперимента из раздела 8 | сверка вернёт `comparison is impossible`, сервер продолжит работать |
| Логи пустые, дамп `psql` не пишет `ERROR` | stderr не перехвачен | в скрипте `psql_db()` добавлено `2>&1`, иначе сообщения СУБД остаются в терминале |
| macOS уснул посреди прогона | долгий прогон | `caffeinate -i ./scripts/run_lr5_experiments.sh` |

Системное время машины не изменялось: смещение часов моделировалось только внутри клиента
(`--offset 7` / `--offset -5`), как требует ЛР №3.
